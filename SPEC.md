# Functional specification, v1

This is the contract for the first release: what a user can do, every endpoint and stream, the event schemas the frontend consumes, the MCP tools agents call, and what v1 deliberately does not do. Each section is written so that an implementation task can cite it. Design rationale lives in `ARCHITECTURE.md` and `docs/decisions/`; the schema in `docs/data-model.md`.

## User-facing features

**Login and invites.** There is no self-registration. The database is seeded with one administrator (`admin`, default password in `README.md`) who must change the password at first login before doing anything else. Admins invite people by email: the invitee receives a link (sent through Resend, or written to the orchestrator log when no API key is configured), opens it, chooses a username and password, and is logged in. Invites expire after 7 days and can be revoked. Login returns a 15-minute JWT access token in the response body and a 30-day refresh token in an HTTP-only cookie. Password reset works the same way as invites: a link by email, a single-use token, valid for 1 hour. Passwords are 10–128 characters. Login is throttled: after 10 failed attempts for one username or one client address within 15 minutes, the endpoint answers 429 for the next 15 minutes; password-reset requests are limited to 3 per identifier per hour and still answer 204. Each user can turn off the escalation emails described under "Task board" on their own settings page.

**Projects.** A user creates a project from a remote URL and, for a private repository, a personal access token. Creation returns immediately with `status: cloning`; the project list shows progress and turns `ready` or `error`. A ready project shows its default branch, last fetch time, its profiles, sessions, shared directories, task states and task board. Shared directories are named directories that every session of the project gets mounted read-write at a container path of the user's choice, typically a build directory such as Cargo's `target` (ADR 0015); the project page lists them, adds and removes them, and can empty one while no session is running. Deleting a project deletes its sessions, tasks, secrets, shared directories, CLI state directory and mirror.

**Agent profiles.** Every project starts with four profiles on the built-in Claude image, each with a system prompt copied into the project at creation ("Role profile templates"): `claude`, the default one, a conversational Claude Code session that serves no task state, which the launch form preselects so a person can just talk to Claude in the project; `planner`, conversational, over `backlog`; and `implementer` over `ready` and `reviewer` over `review`, both ephemeral and marked for automatic dispatch ("Automatic dispatch"), while the `merge` state is merged by the orchestrator ("Automatic merge"). Once an agent credential is stored for the project or for everyone, a new project's task put in `ready` therefore travels to `done` with nobody launching anything; until then the implementer and the reviewer wait, and a person can still launch them by hand (ADR 0051). Users can edit a profile's name, model, system prompt, image, runtime, MCP tool allow-list, declared secrets (extra ones the agent's job needs; the agent's own credential is never declared), served task states, partial-message flag (default on for conversational, off for ephemeral) and idle timeout, and create further conversational profiles. A profile's served states and its system prompt together define its role: a planner serves `backlog` and hands tasks to `ready`, a reviewer serves `review` and hands them to `merge` or back to `ready`. An ephemeral profile runs one prompt and ends: a user launches it from a task's detail view ("run once") or from the project page with a message, and its session shows the transcript, result and cost but has no composer.

**Sessions.** A user launches a session from a profile and a base ref (default: the task's current hand-off commit when present, otherwise the project's default branch), optionally with a first message, and optionally for one task: the session then starts holding that task, and the task card links to the session. From a task's detail view the same launch is one click. The session view shows the full transcript with per-tool rendering and nested subagents, a composer for sending messages (including mid-turn), a stop button, and session metadata (state, branch, container, CLI session id). Sessions keep running when nobody is watching; anyone opening a session later sees everything that happened. A parked session looks like a running one that is waiting; sending a message relaunches it. A session's title defaults to the task's title when launched for a task, otherwise to the first line of the first message (at most 80 characters). The session view also shows cost and token usage so far and a "Changes" panel with the diff of the session branch against its base. Users can end a session, sync its branch into the mirror, and open a terminal into a running session's container.

**Task board.** Per project, a board whose columns are the project's own task states (default `backlog`, `ready`, `review`, `merge`, `needs_human`, `done`, `cancelled`), with dependencies, labels, parent tasks, comments, assignee, the session holding each task, attempt count, and links to the sessions that touched it. Users create, edit, comment, add and remove dependencies, release held tasks, move tasks between states, open a task in a new session, and edit the state list itself. A search field filters cards across columns by title or exact task number (`42` or `#42`). Changes made by agents appear live. A task with open children is blocked until they close and closes itself when the last one does. Every escalation into the human state emails the task's assignee, or every admin when there is none; each user can opt out.

**Automatic dispatch.** An ephemeral profile can be marked for unattended launching, and a new project's seeded `implementer` and `reviewer` come marked ("Role profile templates"; ADR 0051). The dispatcher then watches the task states that profile serves and starts a session on the best claimable task of them by itself, with nobody asking: the task the MCP `ready` tool would have offered that profile first, claimed and launched through the very path a person's launch takes. It reacts to the board as it changes, so a task moved into a served state is normally picked up within a second, and a timer sweeps behind that as the fallback (`DISPATCHER_INTERVAL_SECS`; `README.md`, "Configuration"). Three caps bound it — how many live sessions one profile, one project and the whole instance may have — and every one of them holds automation back only: a launch by a person is never refused by a cap. A project's settings can pause automation outright, which stops every unattended launch in that project while it is set and leaves the sessions already running alone; the project header says so. A task filed by a session — a planner writing tasks over MCP — waits until that session's commits are on the project's default branch, because a dispatched session starts from that branch and would otherwise not have what the task was written against; a task nobody filed from a session, or one whose author made no commits of its own, is not held back, and a person launching the task by hand is never held back (`ARCHITECTURE.md`, "Dispatcher"; ADR 0052). A session nobody launched carries a `dispatcher` tag wherever it is listed, and it authenticates with an agent credential stored for the project or for everyone, since there is no user whose own credential could be resolved ("Agent credentials"; `ARCHITECTURE.md`, "Task tracker" → "Unattended launches"; ADR 0042).

**Automatic merge.** A task state can merge what arrives in it. A new project's `merge` state does: when a reviewer approves a task's hand-off and moves it there, the orchestrator itself — no agent, no session — merges that exact commit into the default branch and closes the task, with a comment naming the commit it merged. When the merge conflicts, the default branch is left alone and the task goes back to the state's conflict state (`ready` by default) with a comment listing the conflicting paths, for an implementer to bring up to date and hand off again. A task that arrives without an approved hand-off goes to the human state instead. The states editor turns the behaviour on or off per state and chooses the conflict state; pausing a project's automation pauses it too. Merged work stays on Mars's own default branch until someone pushes it ("Git operations"; `ARCHITECTURE.md`, "Task tracker" → "Automatic merges"; ADR 0045).

**Round limit.** A task that keeps going round — handed off, sent back by a reviewer or by a conflicting merge, handed off again — stops after `max_rounds` revisions (project setting, default 5): the send-back that would start one more round puts the task in the human state instead, with the reason, and the escalation email goes out as for any escalation. A person's own "request changes" is never redirected, and moving the task out of the human state gives it a fresh allowance. The card shows the round once there has been more than one (`ARCHITECTURE.md`, "Task tracker" → "Rounds"; ADR 0046).

**Scheduled agents.** An ephemeral profile can also carry a cron expression and a prompt, and then runs on the clock with nobody asking: every time the expression comes due, a session of that profile starts with the prompt as its message and no task, titled after the profile and the instant. The expression is five fields — minute, hour, day of month, month, day of week — read in UTC and never in the viewer's zone; the profile editor says so, lists a few examples, and shows the next and last run the server computed, while the profiles list marks the profile with a `schedule` chip. A tick fires once and is never caught up: a run that came due while the orchestrator was down is skipped rather than replayed at startup, and a tick the caps, the pause or a missing credential refuse is spent all the same — the next occurrence is the retry, because a schedule says "run at these times" and not "run this many times". Everything else is what "Automatic dispatch" describes: the same three caps, the same project pause, the same requirement of an agent credential stored for the project or for everyone, and a `schedule` tag wherever the session is listed ("Agent profiles" → "Scheduled profiles"; `ARCHITECTURE.md`, "Task tracker" → "Scheduled agents"; ADR 0043).

**Git operations.** From a session or from the project page, a user can list session branches in the mirror, merge a session branch into a target branch, rebase a session branch onto a target, and push a branch upstream. Conflicts are reported with the conflicting paths, and a conflicting merge started from the UI offers `Resolve with an agent`: a conversational session launched from the merge's target with a generated first message naming the source ref, its commit and the conflicting paths, which merges the source into its own branch and resolves the conflicts while a person merges that branch into the target like any other ("Role profile templates" → `resolver`). The diff of any branch against its base can be viewed, and after a push to a GitHub remote the UI links to the compare page for opening a pull request.

**Secrets.** A write-only manager at global, project and user scope: create, replace, rename, delete, and list names with metadata (scope, created, updated, orchestrator-only, key version, last use). The value is never shown after entry, and a value being typed lives only in the form it is typed into: closing that form, by any route, is what drops it. A deleted secret leaves the list with the request that deleted it rather than with the refetch behind it, so no row offers actions on something that is gone. The list of a secret's recent uses grows in place — a longer page loads with the rows already on screen still there.

**Agent credentials.** What agents authenticate with — for Claude Code a subscription token or an Anthropic API key — is set up on the Secrets page through a guided form: pick the kind, paste the value, choose whether it applies to you, to one project or to everyone. No name is typed and no profile is edited; every session picks up the most specific credential that applies to the user who launches it. The profile editor and the launch form say which credential a launch would use, or that there is none, before anything is launched (ADR 0036).

**Users (admin).** List and delete users, toggle admin, send and revoke invites.

**Dashboard.** The home page lists running and parked sessions across all projects and every task waiting in a human state.

## Authentication

Identical in shape to a conventional JWT plus refresh cookie scheme:

- `POST /api/auth/login` and `POST /api/auth/accept-invite` return `{ user, access_token }` and set the `refresh_token` cookie (`HttpOnly`, `SameSite=Lax`, `Path=/`, `Secure` when `PUBLIC_URL` is https).
- The access token is a JWT signed with `JWT_SECRET`, claims `sub` (user id), `auth_version`, `username`, `admin`, `must_change_password`, `iat`, `exp`. It is sent as `Authorization: Bearer`. Every authenticated HTTP request validates the signature and expiry, loads the current user, and requires the claim's `auth_version` to match `users.auth_version`; a missing user or version mismatch returns 401. Authorization uses the current database values of `admin` and `must_change_password`, not the token snapshots. Demotion takes effect on the next request (403 for an admin-only action); deletion takes effect on the next request (401). Requests already authorized before the change may finish.
- While the current user's `must_change_password` is true, every authenticated endpoint other than `POST /auth/login`, `POST /auth/logout`, `POST /auth/refresh`, `GET /users/me` and `POST /users/{id}/password` answers 403 with error `password change required`. The frontend routes such a user to the change-password page. Changing the password clears the flag; a self-service password change issues a fresh token pair under the revocation rules below.
- Three error strings are part of the contract and are sent byte for byte, because clients may match on them (the frontend routes on `password change required`): `authentication required` (401, every failed authentication — a missing or malformed `Authorization` header, a token that does not verify, an expired token, a deleted user, a superseded `auth_version`, and a missing, unknown, revoked or expired refresh cookie alike, so a caller cannot learn which), `admin required` (403, both an administrator-only route and a self-service-or-administrator route aimed at somebody else) and `password change required` (403, the gate above). One spelling each: the orchestrator defines them once, in its prelude.
- `POST /api/auth/refresh` rotates the refresh token (old one revoked) and returns a new pair using the current user values. A missing user or expired/revoked refresh token returns 401 and clears the cookie. Whether the presented token is still usable — unrevoked and unexpired — is decided by the lookup query that re-reads it inside the transaction holding the user-row lock, never by a check on a row read before that lock.
- Every successful password change or reset updates the password hash, increments `users.auth_version`, revokes all existing refresh tokens and invalidates all outstanding password-reset links in one transaction. This applies to self-service changes, an admin changing another user's password, and reset links. A self-service change requires `current_password` and creates a replacement refresh token in that transaction, then returns its cookie and a matching access token after commit; this browser stays signed in. Changing another user's password returns 204 without changing the acting admin's credentials. Reset by link returns 204 without logging the user in; they then log in with the new password. Role changes alone preserve ordinary logins. Login, refresh, reset-link issuance and password mutations serialize on the user row and revalidate credentials after locking, so a concurrent refresh or login cannot escape revocation with an old credential (ADR 0025).
- The throttled "client address" is the leftmost `X-Forwarded-For` entry when that header is present — nginx sets it in the documented deployment — and otherwise the socket peer address, falling back to the loopback address when there is neither. A malformed header value falls back the same way. `POST /auth/login` answers 429 with error `too many login attempts` while either the submitted username or the client address is blocked, without verifying the password and without extending the block; the username key is trimmed and case-sensitive, the password-reset identifier is trimmed and lower-cased, and a throttled reset request is dropped silently and still answers 204. Both counters live in orchestrator process memory: v1 runs a single instance ("Non-goals for v1"), so there is no shared store and a restart clears them.
- WebSocket and SSE endpoints cannot receive headers from the browser, so they accept the access token as `?token=` and validate it exactly like the header. nginx must not log query strings for those locations.
- Token signature and expiry are checked when a stream opens; an open stream is not closed merely because that token later expires. Account existence, `auth_version` and the password-change gate are checked again before every incoming WebSocket application message (including terminal bytes), and at the existing WebSocket ping / SSE keepalive ticks (30 / 15 seconds). A failed authorization check closes the stream; WebSocket sends the existing `error` message with `authentication required` and closes with code 1008. Dispose of that socket's terminal attachment and stop forwarding its input/output. Already-running agent sessions are unaffected. Database failures must not authorize input or continued streaming; close and let normal retry handle them. On reconnect the client authenticates again, and how depends on what the close was. The upgrade is refused before it happens — the token (401, 403) and the session row (404) are answered with an HTTP status, and the browser hands JavaScript none of it: an expired token and a deleted session both arrive as a close with code 1006 and no `open`. The client therefore rotates its token directly only where something said the credentials were the problem: the authentication close above (`error { authentication required }`, 1008), and, for SSE, the first error of a run of failures, `EventSource` never disclosing which error it is. For the first close of a run whose attempt never reached `open` it reads the resource once over REST before trying again: that read goes through the HTTP client, which rotates the access token if and only if it really is expired — and adopts one another caller has already installed rather than rotating again — so the next attempt carries a current token without a rotation being spent on a guess, and a 404 or 403 ends the attempts there and then, visibly, instead of after a whole schedule of them. Reconnection is bounded and its end is visible. A second authentication close carrying a token this browser has just rotated is not a token problem: the client reads the resource once over REST and, when that succeeds, stops with a visible refusal for this stream rather than signing the user out, which is also how a stream refused by a failed re-authorization read (a database failure closes as 1008) is told apart from a revoked account. Attempts that never open are read once more at a documented count and give up at a second; a resource that still reads keeps them going, and a run that exhausts the bound ends in the same visible state with a reconnect action. A 401 from a refresh clears local authentication, closes other streams and routes to login instead of retrying indefinitely; transient network/server failures retain normal backoff. No state ever claims a reconnect that has no attempt pending. A successful self-service password change installs its new pair before reopening streams; an ordinary refresh rotation — the one an expiring access token causes on any REST 401 — installs its pair without touching open streams, which keep their connection and its terminal attachment and pick the new token up only at their next connect. A token another tab of the same browser installed is adopted under the same two rules, told apart by the token's `sub` claim: the same subject is that tab's ordinary rotation and touches no open stream, a different one is another account and reopens them. Revocation detection on idle streams can lag by one heartbeat interval; there is no separate revocation broadcast service.
- The MCP listener uses per-session bearer tokens, never user JWTs (`ARCHITECTURE.md`, "MCP design"). Each actual session process launch, resume or conversational retry generates a fresh token, replaces its stored hash and writes matching MCP configuration before starting the process. Subsequent requests using the replaced token fail authentication. Reconnecting the orchestrator to an already-running process preserves its token; browser reconnection and user-login changes do not rotate it (ADR 0029).

## REST API

All routes are under `/api`. Responses are bare JSON: arrays for lists, objects for single resources. By default, creates return `201` with the created resource, deletes return `204`, and everything else returns `200`; explicit statuses in the endpoint tables take precedence, including `202` for asynchronous input and stop requests. Errors are `{ "status": <u16>, "error": "<message>" }` with the same status code on the response; git-conflict responses also include `conflicts`.

| Status | Used for |
| --- | --- |
| 400 | Validation failures and malformed input, including a body, path segment or query string that does not parse (an id that is not a UUID), which answers in the same JSON error shape. |
| 401 | Missing or invalid token. |
| 403 | Authenticated but not permitted (non-admin on admin routes, tool not allowed for profile). |
| 404 | Unknown resource. |
| 409 | State conflicts: claim lost, session not in a state that accepts the action, duplicate name, dependency cycle. |
| 422 | Git operation failed with conflicts; body includes `conflicts: string[]`. |
| 429 | Login throttled. Password-reset requests still return 204 when throttled. |
| 500 | Unexpected. Never carries internal detail. |

Timestamps are RFC 3339 strings. Ids are UUID strings.

| --- | --- | --- | --- |
| POST | `/auth/login` | — | `{username, password}` → `{user, access_token}` (429 when throttled) |
| POST | `/auth/refresh` | cookie | — → `{user, access_token}` |

| POST | `/auth/reset-password` | — | `{token, password}` → 204 |

### Users (`/api/users`)

| Method | Path | Auth | Body → Response |
| --- | --- | --- | --- |
| GET | `/users/me` | JWT | → `User` |
| PATCH | `/users/me` | JWT | `{notify_email?}` → `User` |
| GET | `/users` | admin | → `User[]` ordered by `username` |
| GET | `/users/{id}` | JWT | → `User` |
| PUT | `/users/{id}` | admin | `{username, admin}` → `User` (409 if demoting the last admin) |
| DELETE | `/users/{id}` | admin | → 204 (409 for the last admin or yourself) |
| POST | `/users/{id}/password` | JWT (self) or admin | `{current_password?, password}` → `{user, access_token}` (self) or 204 (admin) |
| GET | `/users/invites` | admin | → `Invite[]` (open invites) |
| POST | `/users/invites` | admin | `{email, admin?}` → `Invite` (201; 409 if the email has a user or an open invite) |
| DELETE | `/users/invites/{id}` | admin | → 204 (revoke) |
| POST | `/users/invites/{id}/resend` | admin | → `Invite` (new token and expiry, email sent again) |

`User = { id, username, email, admin, must_change_password, notify_email, created_at }`. `Invite = { id, email, admin, invited_by, expires_at, created_at }`; the token is delivered in the email, or in the full logged link when email is unconfigured, and is never included in the `Invite` response. Changing your own password returns a fresh token pair for the new `auth_version`; all previous token pairs are invalidated (see "Authentication").

When `RESEND_API_KEY` is unset, `LogEmailClient` intentionally writes the full invitation or password-reset message, including the usable token-bearing link, to the operator's log at `info`. This is the local-development delivery mechanism and an explicit exception to the secret-logging rule, with no extra opt-in flag. `ResendClient` does not log these links, and email-provider failures do not fall back to logging them. The exception applies only to invitation/reset delivery, not to passwords, access/refresh tokens, session MCP credentials, API keys, or ordinary request/error logging (ADR 0026).

At least one administrator must remain. Both deleting an administrator and changing `admin` from true to false are rejected with 409 if they would remove the last administrator. Self-demotion is allowed when another administrator remains; self-deletion remains prohibited. The check and mutation are one transaction, serialized with other user deletions and administrator-role changes, so concurrent requests cannot each remove one of the final two administrators. A rejected request changes no fields.

### Projects (`/api/projects`)

| Method | Path | Auth | Body → Response |
| --- | --- | --- | --- |
| GET | `/projects` | JWT | → `Project[]` ordered by `created_at` |
| POST | `/projects` | JWT | `{name, remote_url, default_branch?, credential?}` → `Project` (201, `status: cloning`) |
| GET | `/projects/{id}` | JWT | → `Project` |
| PUT | `/projects/{id}` | JWT | `{name?, default_branch?, max_attempts?, max_rounds?, max_concurrent_sessions?, automation_paused?}` → `Project` |
| DELETE | `/projects/{id}` | JWT | → 204 (refused with 409 while any session is `running` or `creating`) |
| POST | `/projects/{id}/retry-clone` | JWT | → `Project` (only from `error`) |
| POST | `/projects/{id}/fetch` | JWT | → `Project` (runs a mirror fetch now) |
| GET | `/projects/{id}/branches` | JWT | → `Branch[]` (integration heads, upstream-tracking refs and session refs) |

`Project = { id, name, remote_url, default_branch, status, status_message, last_fetched_at, max_attempts, max_rounds, max_concurrent_sessions, automation_paused, created_at, has_credential }`. `default_branch` is null while discovery is pending if the caller omitted it; it must resolve to an integration head before the project becomes `ready`. Changing it with `PUT` on a `ready` project checks the name against the project repository and moves that repository's `HEAD` to it in the same request; a name that is not an integration head of the project is 400. On a `cloning` or `error` project the value is stored as given and the clone job validates it. `max_attempts` (1–20, default 3) is how many times a task may be claimed in one state before a release escalates it; see "Tasks". `max_rounds` (1–50, default 5; 400 `max_rounds must be between 1 and 50` otherwise) is how many revision hand-offs a task may go through before a send-back by a session or the system escalates it instead (`ARCHITECTURE.md`, "Task tracker" → "Rounds"; ADR 0046). `max_concurrent_sessions` (at least 1, null by default) is how many live sessions the project may have before an unattended launch is held back, and `automation_paused` (default `false`) stops every unattended launch and every automatic merge in the project while it is set; both are `PUT` only, both bind automation alone and never a launch by a person, and an explicit `"max_concurrent_sessions": null` removes the cap while omitting the key leaves it alone. A `max_concurrent_sessions` below 1 is 400 `max_concurrent_sessions must be at least 1 when set` (`ARCHITECTURE.md`, "Task tracker" → "Unattended launches"; ADR 0042). `credential` on create is stored as the project-scoped orchestrator-only secret `GIT_CREDENTIAL` and is never returned. `Branch = { name, kind: "head" | "upstream" | "session", commit, session_id? }`. Integration heads use names such as `main`; upstream-tracking refs use `origin/main`; session refs use their full name `refs/sessions/<id>`, and an ended session that kept no ref (it made no commits beyond its base, or a hand-off or an integration head holds every one it made; see "Sessions") is not listed. Fetching refreshes upstream-tracking refs without moving integration heads or session refs. Without a task hand-off, the default session base is the integration head named by `default_branch`; callers may explicitly choose an upstream-tracking ref, tag, session ref or commit id instead.

### Shared directories (`/api/projects/{pid}/shared-dirs`)

Directories under `/data/projects/{pid}/shared/<name>` that are bind-mounted read-write at `container_path` in every session container of the project (`ARCHITECTURE.md`, "Storage"; ADR 0015). The list is read at each launch; a running session keeps the mounts it started with.

| Method | Path | Auth | Body → Response |
| --- | --- | --- | --- |
| GET | `/projects/{pid}/shared-dirs` | JWT | → `SharedDir[]` |
| POST | `/projects/{pid}/shared-dirs` | JWT | `{name, container_path}` → `SharedDir` (201; 400 for an invalid name or path; 409 when the name or the path is already used in the project) |
| POST | `/projects/{pid}/shared-dirs/{name}/clear` | JWT | → 204 (empties the directory; 409 while any session of the project is `running` or `creating`) |
| DELETE | `/projects/{pid}/shared-dirs/{name}` | JWT | → 204 (removes the directory and its contents; 409 while any session of the project is `running` or `creating`) |

`SharedDir = { name, container_path, created_at }`. `name` is 1–64 characters matching `[a-z0-9][a-z0-9_-]*` and is the directory name on disk. `container_path` is an absolute, normalised path of at most 4096 bytes (no `.`, `..`, repeated or trailing slashes, no whitespace or control characters) that is not `/data` or below it and is neither equal to nor an ancestor of `/session/work`, `/session/home`, `/session/log` or `/session/mcp.json`, and is not below `/session/mcp.json`, which is a file; it may lie inside `/session/work`. Both fields are trimmed of surrounding whitespace before they are validated and stored. The recommended entries per ecosystem are in `README.md`, "Operating notes".

### Agent profiles (`/api/projects/{pid}/profiles`)

| Method | Path | Auth | Body → Response |
| --- | --- | --- | --- |
| GET | `/projects/{pid}/profiles` | JWT | → `Profile[]` (oldest first) |
| POST | `/projects/{pid}/profiles` | JWT | `ProfileInput` → `Profile` |
| GET | `/projects/{pid}/profiles/{id}` | JWT | → `Profile` |
| PUT | `/projects/{pid}/profiles/{id}` | JWT | `ProfileInput` → `Profile` |
| DELETE | `/projects/{pid}/profiles/{id}` | JWT | → 204 (409 if default or has sessions) |
| GET | `/profile-templates` | JWT | → `ProfileTemplate[]` (the role templates, in the order of "Role profile templates") |

`Profile = { id, project_id, name, kind, backend, model, system_prompt, permission_mode, image, runtime, mcp_tools, secrets, serves_states, partial_messages, idle_timeout_secs, is_default, auto_launch, max_concurrent, schedule_cron, schedule_prompt, last_scheduled_at, next_scheduled_at, created_at, updated_at }`. `ProfileInput` is the same without ids, timestamps, `last_scheduled_at` and `next_scheduled_at`, which are the scheduler's and are read-only ("Scheduled profiles" below); `permission_mode` must be `bypass`; `mcp_tools` entries must be known tool names; `secrets` entries must be secret names and must not be an agent credential name of any backend (400 `<NAME> is an agent credential and is injected automatically`; "Secrets"); `serves_states` entries must be names of the project's `queue` states (400 otherwise) and default to `["ready"]`. Only `name` is required: `kind` defaults to `conversational`, `backend` to `claude`, `permission_mode` to `bypass`, `image` to `SESSION_IMAGE_DEFAULT` (`README.md`, "Configuration"), `idle_timeout_secs` to 1800, `partial_messages` to the kind's default, `auto_launch` to `false`, `max_concurrent` to 1 and `is_default` to `false` on `POST` and to the stored value on `PUT`; `name` is 1–64 characters, `model` at most 100, `image` at most 255, `system_prompt` at most 64 KiB, `idle_timeout_secs` at least 1, and `model` and `runtime` must not be blank when given. Repeated `mcp_tools`, `secrets` and `serves_states` entries are stored once. A new project already has four of these — `claude`, its default, serving no state, and one per queue state but `merge` — with the prompts of "Role profile templates"; `GET` returns them in the order that section's table lists them. `is_default: true` moves the flag from the project's current default; a project always keeps one, so clearing it on the default is 409. `PUT` replaces the whole profile rather than patching it, so every field the body omits takes its default again — `serves_states` back to `["ready"]`, `mcp_tools` and `secrets` back to empty, `model` and `runtime` back to null, `auto_launch` back to `false`, `max_concurrent` back to 1 and the schedule cleared — with `is_default` the one exception.

`auto_launch` lets the dispatcher start a session of this profile by itself and `max_concurrent` caps how many live sessions of it an unattended launch may leave behind (`ARCHITECTURE.md`, "Task tracker" → "Unattended launches"; ADR 0042). Three rules, on `POST` and `PUT` alike: `auto_launch: true` on a profile whose `kind` is not `ephemeral` is 400 `auto_launch requires an ephemeral profile`; a `max_concurrent` below 1 is 400 `max_concurrent must be at least 1`, on any profile, because the scheduler reads the cap whether or not `auto_launch` is set; and `auto_launch: true` is 400 `auto_launch requires this backend's agent credential at global or project scope` unless the profile backend's agent credential is stored at `global` scope or at this project's `project` scope — a `user`-scope credential does not satisfy it, since an unattended launch has no user to resolve one for ("Secrets"; ADR 0036). The credential may be deleted afterwards, so the jobs check again at launch.

**Scheduled profiles.** `schedule_cron` launches an ephemeral session of the profile periodically with nobody asking, and `schedule_prompt` is the `message` that run is given (`ARCHITECTURE.md`, "Task tracker" → "Scheduled agents"; ADR 0043). The expression is a standard **5-field** cron — minute, hour, day of month, month, day of week — evaluated in **UTC**, always; the finest period it can express is one minute, which is the scheduler's own tick, so nothing a caller can write is too fine to be honoured. The rules, on `POST` and `PUT` alike:

- anything but five plain fields — a seconds field, a year field, `@daily`, `@reboot`, fewer than five fields — is 400 `schedule_cron must be a 5-field cron expression (minute hour day-of-month month day-of-week) evaluated in UTC, with no seconds field, no year field and no @-form`, and five fields the parser refuses are 400 `schedule_cron is not a valid cron expression: <detail>`;
- `schedule_cron` without a non-blank `schedule_prompt` is 400 `schedule_prompt is required when schedule_cron is set`, and a `schedule_prompt` with no `schedule_cron` is 400 `schedule_prompt requires schedule_cron`; a blank prompt with no expression is not an error, it is the profile having no schedule. The prompt is at most 64 KiB (400 `schedule prompt must be at most 65536 bytes`);
- a schedule on a profile whose `kind` is not `ephemeral` is 400 `schedule_cron requires an ephemeral profile`, and a schedule is 400 `schedule_cron requires this backend's agent credential at global or project scope` unless that credential resolves without a user — the same rule, the same lookup and the same two scopes as `auto_launch`, worded after the field that was set.

`last_scheduled_at` is when the scheduler last decided a tick of this profile fires. It is read-only: a value in the body is ignored, the job is its only writer, and a save that **clears** the schedule clears it too, while a save that only changes the expression keeps it. `next_scheduled_at` is computed on every read — the first occurrence of `schedule_cron` strictly after now, in UTC, RFC 3339 — so no client needs a cron parser; it is null for a profile with no schedule and for one whose stored expression can never fire. Clearing a schedule is the ordinary full replacement: a `PUT` body with neither field leaves all three columns null.

`ProfileTemplate = { name, kind, backend, serves_states, mcp_tools, system_prompt, is_default, auto_launch, schedule_cron, schedule_prompt }` is one role template of "Role profile templates", which `GET /profile-templates` serves read-only from the code — no database, no project, the same list for every signed-in caller, in the order of that section's table. It is a top-level path because the templates do not depend on a project. A profile is created from one by sending those fields to `POST /projects/{pid}/profiles` like any other body; there is no endpoint that instantiates a template. `schedule_cron` and `schedule_prompt` are both null on a template a person launches and both set on a scheduled one ("Scheduled profiles"), whose `kind` is then `ephemeral`. `auto_launch` is a boolean, the profile field of the same name: `true` on a template the dispatcher launches by itself (`implementer` and `reviewer`), whose `kind` is then `ephemeral`, and `false` on every other; like every field but `is_default` it is sent on as it is. A scheduled or auto-launched template is offered to every caller, so a project with no agent credential the jobs could use gets the ordinary 400 of the create endpoint rather than a shorter list — for an auto-launched one that is `auto_launch requires this backend's agent credential at global or project scope`, and the profile can be created with `auto_launch` switched off instead. `is_default` is informational — it says which template project creation makes the project's default — and is not sent on; a `serves_states` entry that the target project renamed or deleted is the ordinary 400 of that endpoint, which the frontend checks against the project's states before it offers the template.

`Session = { id, project_id, profile_id, kind, created_by, launch_source, title, task_id, handoff_id, state, base_ref, branch, container_id, cli_session_id, last_seq, last_activity_at, cost_usd, input_tokens, output_tokens, error, created_at, parked_at, ended_at }`. `kind` is the profile's kind at launch. `launch_source` is `user`, `dispatcher` or `schedule` and records who launched the session: `user` for every launch over this endpoint, the other two for an unattended launch, which has `created_by: null`. It is set once, at creation, and a retry or a resume keeps it; `created_by` alone cannot stand in for it, because deleting a user nulls that field on the sessions they launched (`ARCHITECTURE.md`, "Task tracker" → "Unattended launches"; ADR 0042). `cost_usd` and the token counters are accumulated from `result` events (`ARCHITECTURE.md`, "Cost accounting"). A session becomes `running` as soon as its container is started and stdin is attached; `cli_session_id` is null until the CLI's first `init` event, which a conversational session produces only once it has been sent a message, so `running` with `cli_session_id: null` is an ordinary state and clients render it as such (`ARCHITECTURE.md`, "Launch sequence"; ADR 0032).

With `task_id`, the session claims the task in the same transaction that creates the session row, regardless of the profile's served states (the user chose), and the first input delivered to the CLI is a generated message naming the task (`You hold task #12: <title>. Call get_task to read it before starting.`), followed by `message` if given. The session holds the task until it hands it off, releases it, or ends. If `base_ref` is omitted and the task has a hand-off, selection and claim happen atomically: `handoff_id` records that hand-off and `base_ref` records its full commit id. Otherwise `handoff_id` is null and the explicit base or project default is used. The generated message also includes the current hand-off id, source branch, commit, review status and comment, including when an explicit base overrides it: a second paragraph reading `Current hand-off <handoff id> from session <source_session_id> on branch <source_branch> at commit <commit> (review: <review_status>). Hand-off comment: <comment body>`, with the source-session clause left out when that session was deleted and the comment sentence left out when the comment was. When an explicit `base_ref` overrides the hand-off, a third paragraph reads `Your checkout starts from <base_ref>, not from the hand-off commit; fetch refs/handoffs/<handoff id> before continuing that work.` For a conversational profile the generated message is queued ahead of `message` and is recorded as a `user_message` with `user_id: null`, because nobody typed it. For an ephemeral profile the generated message and `message` are joined by a blank line into the `-p` prompt and no further input is accepted. `task_id` accepts a task's UUID, its per-project number as a string, or that number as a JSON integer; a value that addresses no task of this project is a 404. `title`, when omitted, is the task's title, else the first line of `message` truncated to 80 characters, else null. A `title` given explicitly, on `POST` or on `PUT /sessions/{id}`, is 1 to 200 characters after trimming; anything else is a 400.

The `text` of an input must not be blank and is at most 1 MiB: blank text is a 400 `text must not be empty` and longer text a 400 `text too long`, on this route and over the socket alike. The cap is generous enough for a pasted log and is what keeps one request from deciding how much the orchestrator buffers. `POST /sessions/{id}/retry` accepts an absent, empty or `{}` body as "no message"; its response is the `parked` row the retry produced, even when a `message` has already started the relaunch. `POST /sessions/{id}/end` answers `done` for a conversational session, and `failed` when the run ended that way while the stop was in flight — which is every ephemeral session, since an ephemeral session is never parked (ADR 0003) — because the lifecycle has no `failed → done` edge (`ARCHITECTURE.md`, "Session lifecycle"). Either way the container is gone, the branch has been fetched back and the session holds no tasks. The fetch-back that ends a session keeps `refs/sessions/<id>` only when the session holds work no other retained ref holds: a session whose branch is still at the commit it was cloned from — a planner, a reviewer that forwarded a hand-off without committing — and one whose tip an integration head or a hand-off ref of the project contains — an implementer whose last commit was handed off, a session merged into `main` before it ended — end with no session ref, and one an earlier sync left is deleted. A tip that only an upstream-tracking ref (`origin/<branch>`) or a tag contains does not count, because a fetch can prune those. Such a session is absent from `Branch` and `SessionBranch` listings, naming it as a launch's `base_ref` is a 400 `base_ref does not resolve` (launch from the hand-off or the integration head that holds its work instead), and its diff is still its tip's: empty against the branch it started from when it made no commits, and its work when a hand-off holds it, because its work clone, and `branch`, the name of the branch in it, stay until the session is deleted. A ref kept at the end is not re-examined by any job when its work later lands elsewhere; a later sync, diff or hand-off of the ended session judges it again by the same rule (`ARCHITECTURE.md`, "Git model", Ref ownership and Fetch-back; ADR 0050). `end` is accepted while the session is still `creating` — a user who launched by mistake does not wait for the container — and answers `done`: the launch is cancelled, whatever container it had got as far as creating is removed, and the tasks the session held are released exactly as any other end releases them (`ARCHITECTURE.md`, "Session lifecycle", "A session ended while it is creating"). Only `done` and `failed` are refused, with `session is <state>`. A launch that reaches `running` first is ended from there instead, so the answer is the ordinary `done` and the call takes as long as that stop does.

`base_ref` on `POST` records the name the caller gave — an integration head, an upstream-tracking ref, a tag or a commit id — and not the commit it resolved to; a name that does not resolve in the project repository is a 400. `state` on either list endpoint is one of the five lifecycle values and anything else is a 400. On `GET /sessions/{id}/events`, `limit` defaults to 100 and a `limit` outside 1–500, or a `before` below 1, is a 400; `before` is exclusive, so paging backwards passes the lowest `seq` of the page just received.

### Task states (`/api/projects/{pid}/task-states`)

The columns of a project's board, in order. Every project starts with the default set listed in `docs/data-model.md`, `task_states`. A state's `kind` says what it means to the orchestrator: `queue` states are where agents pick work up, the single `human` state is where escalations land, `terminal` states close a task and satisfy dependencies.

| --- | --- | --- | --- |
| GET | `/projects/{pid}/task-states` | JWT | → `TaskState[]` ordered by `position` |
| POST | `/projects/{pid}/task-states` | JWT | `{name, kind, position?, auto_merge?, conflict_state?}` → `TaskState` (201; 400 for an invalid name or kind or an invalid auto-merge pair; 409 if the name is taken or the project already has a `human` state) |
| PUT | `/projects/{pid}/task-states/{name}` | JWT | `{name?, position?, auto_merge?, conflict_state?}` → `TaskState` (400 if `kind` is given: kind is immutable; 400 for an invalid auto-merge pair; 409 if the new name is taken) |
| DELETE | `/projects/{pid}/task-states/{name}` | JWT | → 204 (409 while any task is in the state, for the `human` state, for the last `queue` state, for the last `terminal` state, and for a state another state names as its `conflict_state`) |

`TaskState = { id, project_id, name, kind: "queue" | "human" | "terminal", position, auto_merge, conflict_state, created_at }`. `name` is 1–32 characters matching `[a-z0-9][a-z0-9_-]*`. A missing `position` appends; an explicit one shifts the states at and after it. Renaming a state renames it everywhere at once, since tasks, profiles and conflict states reference states by id.

`auto_merge` (default `false`) makes the orchestrator merge every unheld, unblocked task in the state whose current hand-off is approved into the project's default branch, and move it to the project's first terminal state; `conflict_state` is the name of the state a task goes to when that merge conflicts, and is null exactly when `auto_merge` is false (`ARCHITECTURE.md`, "Task tracker" → "Automatic merges"; ADR 0045). On `PUT` the two travel together: a body that gives either replaces both, and `"auto_merge": false` clears `conflict_state`; a body with neither leaves them alone. The 400 messages are exact: `auto_merge applies to queue states only` (on a `human` or `terminal` state), `auto_merge requires conflict_state`, `conflict_state requires auto_merge`, `conflict_state must name a queue state of this project` (an unknown name, a `human` or `terminal` state), and `conflict_state must be a different state`. Deleting a state that is some state's `conflict_state` is 409 `state is the conflict state of <name>`. A new project's `merge` state has `auto_merge: true` and `conflict_state: "ready"`; every other default state has `auto_merge: false`. Every change emits a `states_changed` `TaskEvent`. The board refreshes states and tasks together through the same event-triggered REST refresh path used for other task changes (see "Frontend"; ADR 0022).

Tracker mutations from REST, MCP and background jobs are serialized per project and validated against state read after acquiring the project lock. Each logical change, its dependency/parent effects, comments and events commit together. A concurrent request waits, then either succeeds against the resulting state or returns the existing validation/conflict error; it cannot publish a partial change. Different projects proceed independently (ADR 0021).

`Task = { id, project_id, number, title, description, state, priority, blocked, labels, parent_id, assignee_user_id, lease_holder_session_id, lease_since, attempts, rounds, needs_human_reason, handoff: Handoff | null, depends_on: {task_id, kind}[], blocks: id[], created_by_session_id, created_at, updated_at, closed_at }`. `state` is the state's name. `depends_on` lists every outgoing dependency with its kind; `blocks` lists the tasks that have a `blocks` dependency on this one. `created_by_session_id` is the session that filed the task through the MCP `create_task` tool, and `null` for a task a person created or whose author session was deleted; it is the author whose work the dispatcher waits for (`ARCHITECTURE.md`, "Dispatcher"). `TaskDetail = Task & { comments: Comment[], handoffs: Handoff[], children: Task[], sessions: {session_id, first_touched_at, last_touched_at}[] }`. Hand-offs are ordered oldest first. `Comment = { id, task_id, author_user_id, author_session_id, system, body, created_at }`.

A task's state is the queue it waits in, and the lease says who is working on it (`ARCHITECTURE.md`, "Task tracker"). There is no in-progress state: a held task is in progress in whatever state it is in. A user may set any state through `PUT` and is not bound by leases. Changing to a different state hands the task off, which clears the lease and resets `attempts`; a terminal state sets `closed_at` and unblocks dependants; a non-terminal state on a closed task reopens it. Setting the current state is a state no-op: it preserves the lease, `attempts` and `closed_at`, and emits no state-change or escalation event. Other supplied fields are still updated normally; a request with no effective changes emits no task event. A user `release` keeps the state and never escalates; agent and reaper releases escalate to the `human` state once `attempts` reaches the project's `max_attempts`. `rounds` counts revision hand-offs since the task last left the `human` state; a send-back by a session or the system — a forward recording `changes_requested`, or an automatic merge that conflicted — of a task whose `rounds` has reached `max_rounds` goes to the `human` state instead of the requested one ("Code hand-offs and review"; `ARCHITECTURE.md`, "Task tracker" → "Rounds"). A user's `PUT` is never redirected. `priority` is 0 (critical) to 3 (low), default 2. `parent_id` nests one level: a task that has children cannot be given a parent, and a task that already has a parent cannot receive children (400). The parent must be a different task in the same project. These checks include terminal children and apply to both creation and re-parenting. On `PUT`, `parent_id: null` makes a task top-level again and `assignee_user_id: null` unassigns it; an `assignee_user_id` naming no user is 400 `unknown assignee`. Deleting a task is not blocked by its lease, and its children survive it as top-level tasks; losing its last open child does not close a parent, since closure follows a state change. A `blocks` dependency on a non-terminal task marks the dependant `blocked`; the other kinds are informational. A non-terminal child blocks its parent the same way, and when the last open child closes the parent is moved to the project's first terminal state by the system (`state_changed` with actor `system`); a parent is never reopened automatically (`ARCHITECTURE.md`, "Task tracker", "Parents"). `number` is assigned from the project's counter and never reused.

Dependencies are identified by `(task, depends_on, kind)`: the same pair may carry both `blocks` and `discovered_from`, and removing one leaves the other intact. Removing an edge that is not there answers 404 `dependency not found`, which is distinct from the generic 404 `not found` an unknown project, `{id}` or `{dep}` gets: both tasks resolved, so a caller can read the named body as "it is already gone" rather than as a task that vanished. Only `blocks` edges participate in dependency-cycle checks. Deleting a prerequisite removes its incident edges and recomputes every surviving dependant’s `blocked` flag in the same transaction, taking remaining prerequisites and children into account. Emit `dependency_removed` for each affected surviving dependant, plus `blocked`/`unblocked` on any flag change. The deleted task retains its event identity as specified under "TaskEvent" (ADR 0022).

### Code hand-offs and review

A task's current `handoff` identifies committed work for the next agent. State names do not determine whether something is code or whether it has been approved. A planning-only state move needs no hand-off and preserves any existing one.

```ts
type HandoffInput =
  | { kind: "revision"; source_session_id?: string; commit: string; comment: string }
  | { kind: "forward"; handoff_id: string; comment: string;
      review?: "approved" | "changes_requested" };
```

`handoff` requires a different target `state` in the same update (400 otherwise) and a non-empty `comment`. For REST revision publication, `source_session_id` is required and must belong to the task's project. A REST caller is a user and is therefore not lease-bound: they may hand off a task nobody holds or one another session holds — the lease is cleared by the state change — and may name any session of the project with a synced branch as the source, not only a session linked to the task. An MCP caller is a session and may only hand off a task it holds. For MCP it is omitted and derived from the caller; a supplied source session id is rejected. `commit` is a full object id, not a moving ref: sync must produce that exact tip or return 409 / MCP `conflict`. The commit is retained under an internal immutable ref before the task moves. Uncommitted changes are excluded; committing them is the agent's responsibility. The hand-off comment, record, state change, lease release and task events commit together. Sync failure leaves the task and lease unchanged.

The 400 messages for these input rules are exact, and the same for REST and MCP: `handoff requires a different target state` (no `state`, or the state the task is already in), `comment body must not be empty`, `commit must be a full lowercase hexadecimal git object id`, `revision hand-off requires source_session_id`, `source_session_id is derived from the calling session` (an MCP caller supplied one), `source_session_id must name a session of this project` (a revision naming another project's session, or one since deleted), `session has no synced branch yet` (a source session that has produced no branch, such as one still `creating`; an ended session whose work clone is still there is synced first and is never refused this way, even when it kept no `refs/sessions/<id>` because it made no commits beyond its base or another retained ref holds its tip — the hand-off pins that tip like any other commit), and `review applies to forward hand-offs only` (a `review` sent with a `revision`). A malformed body — an unknown `kind`, a missing required field — is a 400 too. Unknown fields are ignored, as elsewhere in the API.

The 409 messages of publication are exact in the same way: `project is not ready` (the project repository is not usable yet, checked before any git work), `task is not held by the calling session` (an MCP caller that does not hold the lease), `session branch tip <tip> does not match commit <commit>` (the synced revision source is not at the requested commit), `handoff_id is not the task's current hand-off` (forwarding anything but the current record, including a task that has none), `commit is not present in the project repository` (the commit is unknown to the mirror or is not a commit), and `task changed during hand-off publication; re-read it and retry` (the task's state, lease holder or current hand-off moved between preparation and publication). MCP reports each of them as `conflict` with the same text, and the 400 messages above as `invalid_argument`.

Forwarding requires `handoff_id` to equal the task's current hand-off (409 / MCP `conflict` otherwise). A forward from a session that records `changes_requested` on a task at its round limit still records the decision on the hand-off but moves the task to the `human` state instead of the requested one, with an `escalated` event; the returned task shows the state it went to ("Tasks"; ADR 0046). It reuses the source branch and pinned commit, and optionally records an explicit review decision on that commit. No decision means the previous review status and reviewer are carried forward. A new revision always resets review status to `unreviewed`; old approvals stay in history. Ordinary moves, releases and automatic parent closure do not change the current hand-off or grant approval.

A user can drop a task's current hand-off with `POST /projects/{pid}/tasks/{id}/drop-handoff` and a non-empty `comment` saying why, so that the task's next launch starts from the project's default branch rather than from work known to be bad. It clears the pointer and nothing else: the task's state, lease, `attempts`, `rounds` and `closed_at` are unchanged, a held task keeps its holder and that session's checkout is left alone, and the dropped record stays in `TaskDetail.handoffs` with its retained ref. The comment is written as the user's, and the change emits `updated`, whose task has `handoff: null`, then `commented`, in one transaction. A task with no current hand-off is 409 `task has no current hand-off`, an empty comment is 400 `comment body must not be empty`, and a task not of the project is 404. There is no MCP tool for it: discarding committed work is a user's decision.

`Handoff = { id, task_id, source_session_id, source_branch, commit, comment_id, review_status: "unreviewed" | "approved" | "changes_requested", reviewed_by_user_id, reviewed_by_session_id, reviewed_at, created_by_user_id, created_by_session_id, created_at }`. Actor and source-session ids may become null after deletion; the source branch, commit and review timestamp remain. Review and creation actors come from authenticated context, never input. `comment_id` points to the comment written with this hand-off. Every state event carries the full task including its current hand-off; the accompanying `commented` event carries the comment.

Example: an implementer moves a task to `review` with a revision hand-off at commit A. The reviewer launches from A and forwards that hand-off to `merge` with `review: "approved"`. The task merge uses A, even if the implementer's branch has since advanced to B. To include B, publish a new revision and review it. A rejection forwards A with `changes_requested` to the chosen implementation state; the next implementer starts from A and publishes a new unreviewed revision after fixes.

### Git (`/api/projects/{pid}/git`)

| Method | Path | Auth | Body → Response |
| --- | --- | --- | --- |
| GET | `/projects/{pid}/git/session-branches` | JWT | → `SessionBranch[]` |
| GET | `/projects/{pid}/git/history` | JWT | `?branch=&before=&limit=` → `HistoryEntry[]` (`branch` defaults to the project's default branch, `limit` to 50) |
| GET | `/projects/{pid}/git/diff` | JWT | `?head=&base=` or `?handoff_id=&base=` → `Diff` (`base` defaults to the project's default branch) |
| POST | `/projects/{pid}/git/merge` | JWT | `MergeInput` → `{commit}` or 422 `{status, error, conflicts}` (409 for stale or unapproved task hand-off) |
| POST | `/projects/{pid}/git/rebase` | JWT | `{branch, onto}` → `{commit}` or 422 `{status, error, conflicts}` |
| POST | `/projects/{pid}/git/push` | JWT | `{ref, remote_branch?, force?: boolean = false}` → `{remote_branch, commit}` |
| POST | `/projects/{pid}/git/revert` | JWT | `{branch, to, expected_head, reopen?: {state, comment}}` → `{commit, reverted: HistoryEntry[], reopened: Task[]}` (409 `branch has moved`, 409 `nothing to revert`) |

`SessionBranch = { session_id, ref: "refs/sessions/<id>", commit, ahead, behind, base: default_branch, updated_at }`, one per session ref in the project repository: every live session that has synced, and every ended one that made commits beyond its base that no integration head or hand-off ref contains; any other ended session has no ref and no entry. Ahead/behind is measured against the Mars integration head named by `default_branch`. `source`, `head` accept a session id, integration branch name or upstream-tracking name such as `origin/main`; `onto`, `base` accept integration or upstream-tracking branch names. `branch`, `ref` accept a session id or integration branch name; `target` accepts an integration branch name. Fully qualified refs in these namespaces are accepted to disambiguate names; upstream-tracking refs cannot be mutation targets or push sources (400). Merging `origin/main` into `main` explicitly integrates fetched upstream changes. `Diff = { base, head, merge_base, files: {path, status, additions, deletions}[], patch, truncated }`; a session `head` is synced first and compared at the commit that sync answers, the tip of the branch in its work clone — for an ended session with no ref, that is its base commit when it made no commits, so the diff is empty against the branch it started from rather than an error, and its handed-off or merged work otherwise — and `patch` is the unified diff from `merge_base` to `head`, truncated above 1 MiB, with paths spelled literally rather than C-quoted so a non-ASCII name in a `diff --git` header is the same string as the matching `files[].path`. A non-fast-forward push returns 409 and preserves local work; merge/rebase conflicts remain 422 with conflicting paths. A push updates only the selected upstream branch, never all refs. REST force-pushes require explicit `force: true`; MCP additionally requires the profile's `push` permission.

`HistoryEntry = { commit, parents: string[], tree, subject, author_name, committed_at, requested_by: string | null, reverted_by: string | null, tasks: { id, number, title, handoff_id }[], sessions: { id, title: string | null }[] }`, one per commit on the first-parent line of the integration head `branch`, newest first (`ARCHITECTURE.md`, "Git model", History). `parents` lists the first parent first and is empty for a root commit; `tree` is the commit's tree id, so an entry whose `tree` is the head entry's holds the head's current content; `subject` is the message's first line; `committed_at` is the committer date; `requested_by` is the commit's `Requested-By` trailer — `user:<id>`, `session:<id>` or `system` on a commit the orchestrator made — or null. `reverted_by` is the full id of the newest revert commit above the entry on the first-parent line that undid it, or null: a revert commit is one with a single parent, the subject `Revert <branch> to <short to>` a revert writes and a `Requested-By: user:<id>` trailer, whose tree is `to`'s; it undoes every entry strictly between `to` and itself, reverts are applied newest first, and a revert that a newer one undid undoes nothing — the newer one put back content older than it — so a later revert to an older point marks an earlier revert and everything it undid. It is derived from the listing on every request, walking the line from the head down to the end of the page, so an entry undone by a revert on an earlier page is marked too; nothing is stored. `tasks` are the tasks with a hand-off whose commit the entry brought in, each once, naming the newest of its records pinning that commit (a forward copies its commit); `sessions` are those hand-offs' source sessions followed by the session a `Requested-By: session:<id>` trailer names when it is one of this project's, each once. A commit no hand-off pinned has empty lists. `branch` must be an integration head (400 for an upstream-tracking name, a session, a tag or a head the repository does not have). `before` is a cursor: the last `commit` of the previous page, which must be on the head's first-parent line (400 otherwise, including a commit only a merged side branch reaches); the page then starts with the entry after it. `limit` is at most 200 — a larger value is reduced to 200 — and `limit=0` is 400. The listing is read-only and records no `git` event; like every git endpoint, an unknown project is 404 and one that is not `ready` 409.

A revert rolls the integration head `branch` back to the content of an earlier commit `to` by writing **one new commit** on top of it, never by moving the head backwards (`ARCHITECTURE.md`, "Git model", Revert; ADR 0053). The new commit's tree is `to`'s and its only parent is the head, it is made by the bot identity, and its message is `Revert <branch> to <first 12 digits of to>`, then one line per reverted first-parent commit (its first 12 digits and subject, newest first), then a `Requested-By: user:<id>` trailer. `branch` must be an integration head (400 otherwise); `to` and `expected_head` are full object ids (400 `to must be a full lowercase hexadecimal git object id`, and the same for `expected_head`); `to` must be a commit on the head's first-parent line strictly older than the head (400 otherwise, including the head itself, a commit only a merged side branch reaches and one the repository does not have). When the head is no longer `expected_head` the answer is 409 `branch has moved` and nothing is written, so the confirmation the user saw is the one applied. When the head's tree is already `to`'s, the answer is 409 `nothing to revert: <branch> already matches <first 12 digits of to>` and nothing is written — no commit, no ref move, no reopen — since the commit would change nothing; it is decided under the lock after the `expected_head` check. `reverted` is the first-parent range `to..head` as `HistoryEntry[]`, newest first and attributed exactly as the history is, each with `reverted_by` the new commit. With `reopen`, every task attributed in `reverted` that is in a terminal state is moved to `reopen.state` — a queue or human state of the project: an unknown one is 400 as for any state name, a terminal one 400 `reopen state must be a queue or human state` — has its current hand-off dropped as `POST .../drop-handoff` drops it (a task with none keeps none and is not refused), and gets two comments: `reopen.comment` as the user's, once, and a system comment naming the revert commit. An empty `reopen.comment` is 400 `comment body must not be empty`. The events per task are `state_changed`, `updated` (only when a hand-off was dropped), then the two `commented`, all in one tracker transaction taken under the same project git lock as the revert. A task in `reverted` that is not terminal is listed there and not moved. `reopened` is the moved tasks, in the order `reverted` first names them, and is empty without `reopen`. Every 400 and 409 above is decided before anything is written. If the tracker half fails after the head was written, the revert stays — as a failed push never rolls back a merge — and the answer is 500 with the commit named in the orchestrator's log. The revert does not push (`POST .../push` does), records no `git` event because it names no session, and is not offered over MCP: rolling back is a user's decision.

`MergeInput = { target, message? } & ({ source } | { task_id, handoff_id })`; the alternatives are mutually exclusive (400 otherwise). The task form requires the task's current hand-off to match `handoff_id` and be `approved`, and merges its exact retained commit without syncing a newer source-session tip; a hand-off that is not the task's current one is 409 `handoff_id is not the task's current hand-off` and one that is not approved is 409 `hand-off is not approved`, in both cases with the target unchanged, and a `task_id` this project does not have is 404. Without `message` the task form's merge commit reads `Merge handoff <handoff_id> (<source_branch>) into <target>`. The branch form is an explicit generic git action and does not imply task approval. The same profile gate applies to both MCP forms. Internal hand-off refs are not returned as branches; task details expose them by hand-off id. Diff accepts exactly one of `head` or `handoff_id` (400 otherwise); a hand-off must belong to the URL project (404 otherwise, whether the id is another project's or no hand-off at all) and selects its immutable commit without fetch-back.

## WebSocket: session stream

`GET /ws/sessions/{id}?after=<seq>&token=<jwt>`

The server replays every event with `seq > after` from the database, then streams live events. The client keeps the highest `seq` seen and dedupes on it. Messages are JSON text frames except terminal data, which uses binary frames.

Server to client:

| Message | Shape |
| --- | --- |
| event | `{ "type": "event", "event": AgentEvent }` |
| session | `{ "type": "session", "session": Session }` on every state change, and after every `result` event it sends, whose commit moved `cost_usd` and the token counters |
| input_accepted | `{ "type": "input_accepted", "client_id": string, "seq": number }` |
| input_rejected | `{ "type": "input_rejected", "client_id": string, "reason": string }` |
| terminal | binary frame: raw bytes from the exec PTY |
| terminal_closed | `{ "type": "terminal_closed", "exit_code": number }` |
| error | `{ "type": "error", "message": string }` followed by close |

The server also sends one `session` message immediately after the upgrade, before replay, so the client has the current state.

A client validates every text frame against this table before applying any of it, and reads a frame in one of three ways. A frame that is not JSON, is not an object, or whose `type` is known but whose fields do not match the shape above is **malformed**: it is dropped whole, nothing is applied and no cursor moves, because applying half a message and then advancing `seq` past it leaves a transcript with a hole that no reconnect refills. A frame whose `type` this client has never seen is **unknown**: it is ignored, since a `ServerMessage` carries no cursor of its own and there is nothing to lose by skipping one — a tab left open across an orchestrator upgrade is the ordinary case. An `event` whose `AgentEvent.kind` is unknown is neither: it does carry a cursor, so it is accepted, rendered as a `raw` row, and dedupe advances over it as over any other event (see "AgentEvent"). A client's diagnostics for a rejected frame name the field that failed and never its value: a frame carries agent output, and the URL it arrived on carries an access token.

Client to server:

| Message | Shape |
| --- | --- |
| input | `{ "type": "input", "client_id": string, "input": SessionInput }` |
| stop | `{ "type": "stop" }` |
| terminal_open | `{ "type": "terminal_open", "cols": number, "rows": number }` (session must be `running`) |
| terminal_resize | `{ "type": "terminal_resize", "cols": number, "rows": number }` |
| terminal data | binary frame: bytes to the PTY |
| terminal_close | `{ "type": "terminal_close" }` |

`SessionInput` is one of:

```ts
type SessionInput =
  | { kind: "message"; text: string };   // the only kind: the agent never asks the host a question
```

`message` is the only kind, and an unknown one is refused (400 over REST, `input_rejected` over the socket); the same holds for blank `text` and for `text` over the 1 MiB cap (see "Sessions"). The CLI is launched with `--permission-mode bypassPermissions --permission-prompts none` and, as recorded against the pinned version, never waits on stdin for an answer, so there is no `answer` input and no `prompt` event to answer (ADR 0033; `ARCHITECTURE.md`, "Claude Code invocation"). `client_id` is a client-generated string echoed back so optimistic UI can reconcile, at most 128 bytes (over it: 400 over REST, `input_rejected` with `client_id too long` over the socket). `seq` in `input_accepted` is the highest committed sequence at acceptance; the `user_message` event recording the input follows later with the same `client_id`. `POST /sessions/{id}/input` accepts the same `client_id` beside the `SessionInput` fields and echoes it on that `user_message` in the same way, so a client falling back to REST while its socket is closed still reconciles; a body without one is unchanged and produces a `user_message` with no `client_id`. A `message` is accepted for a conversational session in `creating`, `running` or `parked`; ephemeral sessions reject all additional input, matching the REST contract, and a refused input is answered with `input_rejected` carrying the reason. The orchestrator sends WebSocket pings every 30 seconds and closes after two missed pongs.

**Known v1 restart limitation (ADR 0020).** `input_accepted` and HTTP 202 from `/sessions/{id}/input` acknowledge acceptance by the orchestrator, not guaranteed delivery to or execution by the CLI. Input queues are in memory; a restart can lose queued messages or leave delivery uncertain even when a `user_message` is in history. `client_id` is not a durable idempotency key. Reconnecting replays output events but does not automatically resend inputs. There is no new delivery-status UI in v1; users may inspect and manually resend, accepting that this can repeat work.

The terminal is an `exec` with a PTY into the session container running `/bin/bash -l` as the `agent` user, multiplexed onto the same socket with binary frames. It is an escape hatch for inspection; nothing it does is recorded as events.

A `terminal_open` that cannot be honoured (session not `running`, container gone) answers `terminal_closed` with `exit_code: -1`. The socket stays open: `error` is followed by a close, and a terminal that could not start is not a reason to end the transcript stream. The same `exit_code: -1` is what a terminal that ended without the engine reporting a code carries. A second `terminal_open` while one is open, a `terminal_resize` or `terminal_close` with none open, and binary frames with none open are all ignored.

## SSE: task stream

`GET /api/projects/{pid}/tasks/stream?token=<jwt>` with optional `Last-Event-ID: <seq>` header (or `?after=<seq>` for the first connection).

`?after=latest` is the cursor of a client that has none: the stream starts at the project's highest committed sequence and replays nothing. The server resolves it after subscribing to the project's notifications, so an event committed in between is either counted by the resolved cursor — and is then in the REST snapshot the client reads once the stream is open — or arrives live. `latest` is a `?after=` value only; `Last-Event-ID` is written by `EventSource` from a frame's `id:` and is always a sequence, so `latest` there is the same 400 as any other non-sequence. A client that has received an event resumes from its sequence as before, and one that has not asks for `latest` again: a project's whole history is never replayed into a board that is about to make an authoritative REST read anyway ("Frontend", "Board refresh ordering").

Each SSE message has `id: <seq>`, `event: task`, and `data: <TaskEvent JSON>`. The response body opens with a `: ready` comment, written before any replay so the first body byte follows the headers immediately: a stream with nothing to replay must not wait for its first keepalive, because a proxy that holds a response's headers until its first body byte would delay the client's `open` event by that long. Clients ignore comment frames. A `: keepalive` comment is sent every 15 seconds, on its own cadence, unaffected by the opening comment. The server supports replay from `Last-Event-ID`; the browser client disables automatic reconnect and explicitly reopens with a refreshed token and `?after=<lastSeq>` as specified under "Authentication". nginx must serve this location with buffering off.

A client validates every `task` frame before the board sees it: `seq` a safe integer of at least 1, `ts` and `kind` strings, `task_id` a string or null, and `actor` an object with a string `kind`. A frame failing any of those is dropped whole and the cursor stays where it was — a `seq` that is not a sequence would otherwise become `lastSeq` and make every subsequent reconnect ask for a cursor the server answers 400 `BAD_CURSOR` to. An unknown `kind` is accepted: every kind means the same thing to the board — refresh authoritative data — so a kind a newer orchestrator added is already handled correctly by being counted and refreshed on, and rejecting it would leave the cursor behind. As on the session socket, a diagnostic for a rejected frame names no field value.

The server subscribes to project notifications before opening the SSE response, then replays events and follows live changes, with the existing periodic safety read for missed notifications. The board waits for the stream's open event before its initial REST load; when explicitly recreating `EventSource` with a refreshed token it passes `?after=<lastSeq>`, or `?after=latest` when it has no sequence yet. It refreshes authoritative board data on open/reopen and on each new task event, using the loading rules under "Frontend". Historical event `task_id` values, including `deleted` events, survive deletion of the task row.

## AgentEvent

The single schema the frontend sees for every backend. Stored in `events.payload` without `seq`, `ts`, `kind` (those are columns) and reassembled on read. Payload fields whose names start with `_` (such as `_offset`, the transcript byte offset used for recovery) are internal and are stripped before an event leaves the orchestrator.

```ts
interface AgentEventBase {
  seq: number;                 // per-session, monotonic, starts at 1
  ts: string;                  // RFC 3339, orchestrator observation time
  parent_tool_use_id?: string; // present on everything emitted inside a subagent
  message_id?: string;         // backend message id when the backend provides one
}

type AgentEvent = AgentEventBase & (
  | { kind: "init";               cli_session_id: string; model?: string; tools: string[]; mcp_servers: {name: string; status: string}[]; resumed: boolean }
  | { kind: "user_message";       text: string; user_id: string | null; client_id?: string }
  | { kind: "text_delta";         text: string }                                  // partial messages only
  | { kind: "text";               text: string }                                  // complete assistant text block
  | { kind: "thinking";           text: string; redacted: boolean }
  | { kind: "tool_call";          tool_use_id: string; name: string; input: unknown }
  | { kind: "tool_result";        tool_use_id: string; content: string | unknown; is_error: boolean; truncated: boolean }
  | { kind: "permission_denied";  tool_use_id?: string; name: string; reason: string }
  | { kind: "subagent_start";     tool_use_id: string; description: string; agent_type?: string }
  | { kind: "subagent_end";       tool_use_id: string; is_error: boolean }
  | { kind: "result";             subtype: string; terminal_reason?: string; is_error: boolean; num_turns: number; duration_ms: number; cost_usd?: number; usage?: unknown; permission_denials: unknown[] }
  | { kind: "error";              message: string; fatal: boolean }
  | { kind: "state_change";       from: SessionState; to: SessionState; reason: string; signal?: "SIGINT" | "SIGTERM" }
  | { kind: "launch_warning";     message: string }                              // e.g. a declared secret no scope defines, or no agent credential
  | { kind: "git";                op: "sync" | "merge" | "rebase" | "push"; ok: boolean; detail: unknown }
  | { kind: "raw";                backend: "claude"; native: unknown }            // untranslated native line
);
```

`kind` is an open enum: values are only ever added, never removed or renamed, and a browser tab outlives an orchestrator upgrade. A client therefore treats an unknown `kind` as forward-compatible rather than as an error — it renders as an untranslated row, exactly as `raw` does, and the client's `seq` dedupe advances over it — while still requiring the envelope (`seq` a safe integer of at least 1, `ts` a string) and, for a `kind` it does know, the fields it reads off it. An event failing either of those is off-contract: it is dropped whole and the cursor does not move (see "WebSocket: session stream"). A client validates only what it consumes; the shapes above are enforced where they are written.

Agent/tool output and user-provided transcript content may contain secrets. v1 applies no automatic secret detection or redaction before storing or displaying this content, including `tool_call`, `tool_result`, `text`, `thinking`, `user_message` and `raw` payloads (ADR 0027). Normal translation and size limits still apply. The `thinking.redacted` flag reflects backend-provided redaction; it is not a Mars secret-filtering guarantee. Orchestrator-generated diagnostics and event metadata must not copy values from credential handling.

The `git` event's `detail` is one shape per `op`:

```ts
type GitDetail =
  // op: "sync"
  | { ref: string; commit?: string; error?: string }
  // op: "merge"
  | { source: string; target: string; commit?: string; fast_forward?: boolean; conflicts?: string[]; requested_by: string; error?: string }
  // op: "rebase"
  | { branch: string; onto: string; commit?: string; conflicts?: string[]; work_tree?: "updated" | "reconciliation_required" | "not_applicable"; requested_by: string; error?: string }
  // op: "push"
  | { ref: string; remote_branch: string; commit?: string; force: boolean; compare_url?: string; requested_by: string; error?: string };
```

Optional fields are omitted rather than null: `commit`, `fast_forward` and `compare_url` appear when `ok` is true, `conflicts` and `error` when it is false. `ref`, `source`, `target`, `branch` and `onto` are API ref names, except a task merge's `source`, which is the hand-off id. A sync's `commit` is the tip of the session's branch; when a `done` or `failed` session — or the one being ended — is still at its base commit, or its tip is contained in an integration head or a hand-off ref, the sync writes no `refs/sessions/<id>` and removes any, and `ref` still names that ref (`POST /sessions/{id}/end` in "Sessions"). `requested_by` is `user:<uuid>`, `session:<uuid>` or `system`, the same value the commit's `Requested-By` trailer carries. `error` is the generic user-facing message from the same failure the REST call would answer with — never git's stderr and never a credential. The event is written on every session whose ref took part and on the calling session when an agent asked; a task merge takes no session ref, so its participant is the hand-off's source session, when that session still exists (`ARCHITECTURE.md`, "Git model", Merge, rebase, push).

Translation rules for the Claude backend, from `stream-json` lines. Every rule below is measured against the native shapes recorded from the pinned CLI version (`images/claude/VERIFY.md`, "Observed on 2.1.274"; the recording itself is `images/stub/fixtures/default.jsonl`), and a line the translator drops is still in the transcript file on the session volume.

- `system`/`init` → `init`, **once per process**. The CLI writes an `init` line at the start of every turn, all carrying the one `session_id` of the process; under `--input-format stream-json` even the first of them arrives only after the process has read a stdin line, so the event follows the session's first message rather than its launch (`ARCHITECTURE.md`, "Launch sequence"). The first line becomes the event, and each later line that repeats that `session_id` only refreshes the translator's state and produces nothing. A line reporting a different `session_id` is a different conversation and produces a new `init`. `session_id` is stored as `cli_session_id`; `resumed` is true when the launch used `--resume`, which no native field reports — a resumed launch's `init` carries the same field set and repeats the resumed `session_id` (`ARCHITECTURE.md`, "Claude Code invocation"). `model` and `tools` are both present on every recorded `init` of the pinned version; `model` stays optional in the schema so a backend that omits it needs no new kind, `tools` does not. Each `mcp_servers` entry contributes its `name` and its `status` verbatim; the native entry's `source` (where the CLI found the server, `dynamic` for one passed with `--mcp-config`) is not forwarded. An unreachable server is reported with `status: "failed"`, which is one of the statuses the launcher's `launch_warning` covers (`ARCHITECTURE.md`, "MCP design").
- `system`/`permission_denied` → `permission_denied`, taking `name` from `tool_name`, `tool_use_id` from `tool_use_id` and `reason` from `message`. The line carries no `decision_reason`, and `decision_reason_type` is not forwarded. A `tool_result` with `is_error: true` follows and is translated as any other tool result.
- `system` subtypes that report the CLI's own progress — `status`, `thinking_tokens`, `api_retry`, `task_started`, `task_progress`, `task_updated`, `task_notification`, `vcs_state_changed` — produce no event: the `task_*` run is what `subagent_start`, the subagent's own events and `subagent_end` already describe, and the rest is per-request telemetry. An `api_retry` line still feeds the authentication rule below. Any other `system` subtype → `raw`.
- `rate_limit_event` (a top-level type) produces no event: it reports the account's rate-limit windows and utilisation, which belongs to the credential rather than to this session's transcript. Like every native line it is never logged above `debug` and never with its fields.
- `assistant` messages → one event per content block: `text`, `thinking`, `tool_call`. A `thinking` block whose text is empty produces nothing — the pinned CLI forwards a `signature` and no text, and an event with nothing to read is not stored — while a `redacted_thinking` block still produces `thinking` with `redacted: true`. A `tool_call` whose name is the subagent tool additionally emits `subagent_start`. The subagent tool has been called `Task` and `Agent` in different CLI versions (2.1.274 and 2.1.282 list it as `Task` in `init.tools` and name it `Agent` in the `tool_use` frames they write); the translator matches both from one constant, and a fixture per pinned CLI version proves the constant is still right.
- `user` messages produced by the CLI (tool results) → `tool_result` per block; a result for a subagent tool call additionally emits `subagent_end`. A `user` line never produces a `user_message`: that kind is written by the owner when it writes the input. A `user` line whose content is only text is one of three things: the CLI's echo of a message the orchestrator wrote, dropped by matching on content hash; `[Request interrupted by user]`, the line a stop produces, dropped because the `state_change` written for the stop already says it (`ARCHITECTURE.md`, "Stop semantics"); or a message the orchestrator did not write, kept as `raw`. The first frame of a subagent is such a line, carrying the subagent's prompt and its `parent_tool_use_id`; a line with a `parent_tool_use_id` is never matched against the input hashes, because an input the orchestrator wrote goes to the top-level conversation.
- `stream_event` (only with `--include-partial-messages`) → `text_delta` for a `content_block_delta` whose delta is a `text_delta`. Every other stream event is dropped because the complete block follows in the `assistant` message: `message_start`, `message_delta`, `message_stop`, `content_block_start`, `content_block_stop`, and the `thinking_delta`, `signature_delta` and `input_json_delta` deltas.
- `result` → `result`, with `cost_usd` taken from the native `total_cost_usd` and `terminal_reason` passed through as the CLI wrote it (`completed` for a turn that ended by itself, `aborted_streaming` for one a stop interrupted). `total_cost_usd` is cumulative for the process and, on a resumed process, for the conversation it resumed, so the owner accumulates its increase over the previous `result`, while `usage` is the turn's own and is summed as it arrives (`ARCHITECTURE.md`, "Cost accounting"). Each entry of `permission_denials` — `{tool_name, tool_use_id, tool_input}` — additionally produces a `permission_denied` event, unless the turn's own `system`/`permission_denied` line already reported that `tool_use_id`. For an ephemeral session the owner then stops the container and emits a `state_change` to `done`.
- Authentication failure → one `error` with `fatal: true`, at most once per process. The CLI reports a rejected credential as a run of `system`/`api_retry` lines with `error_status: 401` and `error: "authentication_failed"`, then a synthetic assistant message and a `result`, and exits 1; the event is emitted on the first line that reports it and names the injected variable and its scope, never a value (`ARCHITECTURE.md`, "Claude Code invocation", Credentials). A `result` is only read for this when it has `is_error: true`, so an agent that discussed an authentication error cannot park its own session.
- Anything else → `raw`.

Every event emitted from a native message that carries `parent_tool_use_id` copies it. The frontend groups events by that id under the corresponding `tool_call`.

## TaskEvent

```ts
interface TaskEvent {
  seq: number;                 // per-project, monotonic
  ts: string;
  task_id: string | null;      // original task UUID, retained after deletion; null on "states_changed"
  actor: { kind: "user"; user_id: string } | { kind: "session"; session_id: string } | { kind: "system" };
  kind: "created" | "updated" | "state_changed" | "claimed" | "released" | "escalated"
      | "blocked" | "unblocked" | "commented" | "dependency_added" | "dependency_removed"
      | "deleted" | "states_changed";
  task?: Task;                 // full task after the change; absent on "deleted" and "states_changed"
  comment?: Comment;           // on "commented"
  from?: string; to?: string;  // state names, on "state_changed" and "escalated"
  reason?: string;             // on "released": "given_back" | "session_ended" | "stalled" | "user"; on "escalated": free text
  states?: TaskState[];        // on "states_changed": the project's full state list after the change
}
```

`state_changed` is any hand-off, by an agent, a user, or the system when a parent closes with its last child. `escalated` is a move into the project's `human` state, whether an agent asked for it (`needs_human`), the reaper ran out of attempts, a send-back reached the round limit, or the auto-merge job found a task without an approved hand-off; it carries `from`/`to` like a state change plus the reason. The auto-merge job's merge and its conflict send-back are `state_changed` with actor `system`. `updated` is a change to the task's own fields, including a user dropping its current hand-off ("Code hand-offs and review"). `released` is a lease cleared without a state change. `blocked`/`unblocked` fire when a dependency change or a hand-off flips a dependant's `blocked` flag.

`deleted` carries the original task UUID in `task_id` and omits `task`; earlier events keep their original identifiers and payloads. The board deduplicates by `seq` and uses events as refresh signals, never applies historical `task` or `states` payloads over a REST snapshot, and stores no raw event queue (ADR 0022). This includes `states_changed`, which refreshes both columns and cards.

## MCP tool contracts

Served at `http://orchestrator:7001/mcp` (Streamable HTTP), bearer-authenticated per session. The session context supplies `session_id`, `project_id` and the profile. Tools are listed to a session only if allowed for its profile; task tools are always allowed. Successful tracker changes commit their `TaskEvent` rows and the calling session's link to the directly changed task together. `ready` and `get_task` do not write tracker events, create session-task links, or advance touch timestamps. Rejected tracker operations and updates with no effective changes likewise leave tracker history and links unchanged. `list_session_branches` emits no session `git` event; git operations retain their existing outcome-event contract. Backend-reported tool calls/results remain part of the ordinary transcript, including reads and failures. There is no separate persistent MCP read-audit log in v1 (ADR 0030).

Tool descriptions are part of the contract because they steer the agent. They are reproduced verbatim. So is the server's `instructions` string, which the client receives once per MCP connection at `initialize`:

> Mars task tracker and git tools. This server is the task tracker for this session: it replaces any task tracker, issue tracker or planning tool that the repository's own instructions name, so follow their workflow with these tools instead, never report the other tracker as missing, and never write task files into the repository. Call ready to find work, claim before working, comment before handing off.

Neither the instructions nor any tool description names a particular tracker product: the sentence has to hold for whatever the repository at hand uses, and naming one would invite the agent to look for it (`ARCHITECTURE.md`, "MCP design").

Every `task` argument accepts a task's UUID or its per-project number (as a number or a string such as `"12"` or `"#12"`). A task's `state` in inputs and outputs is the state's name. The tracker's rules (state as queue, lease as worker, attempts) are in `ARCHITECTURE.md`, "Task tracker".

Where a tool section below quotes no message, the answer is the tracker's or the git service's own, in the words the REST endpoint behind the same operation gives: `task is not held by this session` for a caller that holds neither the lease nor the creator exception on `update` and `release` (the hand-off path keeps the `task is not held by the calling session` of "Code hand-offs and review"), `unknown state "<name>"; valid states are: <names in position order>` as `invalid_argument` for an unknown `state`, and `parent must be a top-level task of the same project` as `invalid_argument` for an unusable `parent` on `create_task` or `update`, including one that names no task at all. A `task`, `parent`, `depends_on`, `add_depends_on` or `remove_depends_on` value that is not a task reference at all is `invalid_argument` `task must be a UUID, a number, or "#<number>"`; any other argument that does not fit its type is `invalid_argument` `invalid arguments: <reason>`.

### `ready`

Description: "List tasks you could start now, in the states your profile serves. Claim one with `claim` before doing any work on it. If you were launched for a task you already hold it: call `get_task` on it instead."

Input `{ limit?: number = 20 }`. Output `{ tasks: TaskSummary[] }` where `TaskSummary = { id, number, title, state, priority, labels, description_excerpt, attempts, depends_on_count }`. Returns tasks in the calling profile's served states that are not blocked and have no lease holder, ordered by `priority` then `number`. A profile that serves no states gets an empty list.

An explicit `limit` must be an integer from 1 through 100 inclusive; other values return `invalid_argument` and are never clamped. To produce `description_excerpt`, trim the description, replace each newline sequence (CRLF, LF or CR) with one space, then take the first 200 Unicode scalar values and trim trailing whitespace, without adding an ellipsis. `depends_on_count` counts outgoing dependencies of every kind.

### `claim`

Description: "Claim a task before you start it. You hold it until you hand it off with `update`, give it back with `release`, or your session ends. If the claim fails someone else has it: pick another."

Input `{ task: string | number }`. Output `{ task: Task }` or MCP error `conflict` with message "task is not claimable" when the atomic update returns zero rows. Only tasks in the profile's served states can be claimed; a task outside them returns `conflict` with message "task is not in a state this profile serves". The returned task includes its hand-off. Claiming in an existing session never resets its checkout; the agent must fetch and inspect the recorded commit before reviewing or continuing that work. The retained ref can be fetched from the session clone's `origin` as `refs/handoffs/<handoff.id>`.

### `get_task`

Description: "Read a task in full: description, comments, dependencies, sub-tasks and which sessions worked on it. Read it before you start; the comments are where earlier agents and humans left context for you."

Input `{ task: string | number }`. Output `{ task: TaskDetail }` (same shape as REST).

### `update`

Description: "Update a task you hold. Changing to a different `state` ends your hold. When handing over code, commit it first and include a revision hand-off with the exact commit and a comment describing the work and checks. When reviewing, forward the existing hand-off with your decision; do not substitute your own branch."

Input `{ task: string | number, state?: string, title?: string, description?: string, priority?: number, labels?: string[], parent?: string | number | null, add_depends_on?: string[], remove_depends_on?: string[], handoff?: HandoffInput }`. Output `{ task: Task }`. Rules: the caller must hold the lease, except for `title`, `description`, `labels`, `add_depends_on` and `remove_depends_on` on tasks the caller created that nobody holds. `state` must be one of the project's states; an unknown name returns `invalid_argument` with the valid names in the message. Changing to a different state releases the lease and resets `attempts`; a terminal state also sets `closed_at` and recomputes `blocked` on dependants. Setting the current state preserves the lease and counters, as in REST. The same one-level parent rules apply; invalid nesting returns `invalid_argument`. Hand-off inputs obey "Code hand-offs and review", whose exact 400 and 409 messages are returned here as `invalid_argument` and `conflict` with the same text; revision publication uses the calling session and requires no git-tool permission, because it only syncs and retains committed work inside the project. `add_depends_on` creates `blocks` dependencies; a cycle returns `invalid_argument`, an entry naming no task of the project returns the generic `not_found` the REST dependency endpoint gives an unknown `{dep}`, an entry whose end is in another project returns `invalid_argument` `dependency must reference tasks of the same project`, and an edge that is already there returns `conflict` `dependency already exists`. `remove_depends_on` removes only `blocks` edges, preserving any provenance or related edge for the same pair; a named task with no `blocks` edge to remove returns `not_found` with the same `dependency not found` message the REST endpoint gives, so the agent can tell it apart from a task it named wrong.

### `release`

Description: "Give a task back without finishing it, and say why. Use this when you cannot make progress. The task stays in its state for another agent; after too many attempts it goes to a human instead."

Input `{ task: string | number, reason: string }`. Output `{ task: Task }`. The caller must hold the lease. The reason is recorded as a comment. If `attempts` has reached the project's `max_attempts`, the task moves to the project's `human` state with `needs_human_reason` set, and the output `task` shows that state.

### `comment`

Description: "Leave a comment on a task. This is how you talk to other agents and to humans: say what you found, what you changed, what you need. Comment before you hand off."

Input `{ task: string | number, body: string }`. Output `{ comment: Comment }`. Any session in the project may comment on any task.

### `needs_human`

Description: "Hand a task to a human when you are blocked on a decision, credentials, or anything you must not decide alone. Say exactly what you need."

Input `{ task: string | number, reason: string }`. Output `{ task: Task }`. Moves the task to the project's `human` state, sets `needs_human_reason`, releases the lease and resets `attempts`. Requires holding the lease or the task being unheld. If it is already in the human state, record the reason and explicitly release any held lease, but preserve `attempts`; emit `commented`, `updated` and, when applicable, `released`, with no new `escalated` event or escalation email. This explicit release action is distinct from assigning the current state through `update`.

### `create_task`

Description: "Create a task when you discover work outside what you hold: a follow-up, a bug, or a sub-task of a plan. Put it in the state that matches how ready it is (`backlog` if it still needs planning). Link it with `depends_on` if it must wait, and with `parent` if it is part of a larger task. If you hold several tasks, identify the originating task with `discovered_from`."

Input `{ title: string, description?: string, state?: string, priority?: number = 2, labels?: string[], parent?: string | number, depends_on?: string[], discovered_from?: string | number }`. Output `{ task: Task }`. `state` defaults to the project's default state (its first `queue` state); an unknown name returns `invalid_argument`. `depends_on` creates `blocks` dependencies; unlike `update`'s `add_depends_on`, creation resolves every entry inside the project, so an entry naming no task of it — whatever the reason — returns `invalid_argument` `dependency must reference tasks of the same project`, as `POST /projects/{pid}/tasks` does. `created_by_session_id` is set. Resolve provenance after taking the project lock: with no held tasks, omission creates no provenance edge; with exactly one, omission selects that task; with multiple, `discovered_from` is required or the entire request fails with `invalid_argument`. An explicit origin must be a task currently held by the caller in this project. If the selected origin is the new task's parent, the parent link already records provenance and no redundant `discovered_from` edge is added; otherwise add that edge from the new task to the origin. A `blocks` edge to the same origin may coexist. The same one-level parent validation as REST applies; any validation failure creates neither a task nor edges.

### `list_session_branches` (git; profile-gated)

Description: "List session branches in the project mirror with how far ahead/behind they are relative to the default branch."

Input `{}`. Output `{ branches: SessionBranch[] }` (same shape as REST).

### `merge` (git; profile-gated)

Description: "Merge into an integration branch. For reviewed task work, pass task_id and handoff_id to merge the exact approved commit. For an explicit generic branch merge, pass source. Fails with conflicting paths; never resolves conflicts for you."

Input `MergeInput` (same as REST; `task_id` also accepts a per-project task number). Output `{ commit: string }` or error `conflict`, with `data: { conflicts: string[] }` for merge conflicts. The task form rejects stale or unapproved hand-offs as `conflict` with the same `handoff_id is not the task's current hand-off` and `hand-off is not approved` messages the REST endpoint gives, and uses the pinned commit without syncing the source branch. For the branch form, ref names follow the REST git contract: `origin/main` is a permitted source, while the target must be a Mars integration head; every session ref involved is synced first.

### `rebase` (git; profile-gated)

Description: "Rebase a branch onto another in the mirror. Use it to bring a session branch up to date with the default branch before merging."

Input `{ branch: string, onto: string }`. Output `{ commit: string }` or `conflict`. Ref names follow the REST git contract: an upstream-tracking ref may be `onto`, never the branch being rewritten. If `branch` is the calling session's branch, the session work tree is updated afterwards when clean.

### `push` (git; profile-gated)

Description: "Push a mirror branch to the upstream remote. Only do this when a human or the task explicitly asks for it."

Input `{ ref: string, remote_branch?: string, force?: boolean = false }`. Output `{ remote_branch: string, commit: string }`. Only integration heads or session refs may be pushed, and only the selected upstream branch is updated. A non-fast-forward rejection returns `conflict` without changing local refs. Force pushes are refused unless `force` is true and the profile has `push` in `mcp_tools`; session refs are pushed as `refs/heads/session/<id>` by default.

Error codes used across tools: `unauthorized` (bad token), `forbidden` (tool not in profile), `not_found`, `conflict`, `invalid_argument`, `internal`. A tool failure is a JSON-RPC error object, never a result with `is_error`; its `message` is the text quoted in the tool sections above, and its `data.code` is the string code:

| `data.code` | JSON-RPC `code` |
| --- | --- |
| `unauthorized` | -32001 |
| `forbidden` | -32003 |
| `not_found` | -32004 |
| `conflict` | -32009 |
| `invalid_argument` | -32602 |
| `internal` | -32603 |

`data.code` is always present; `data.conflicts` (a list of paths, in git's order) is present only on a `merge` or `rebase` that stopped on conflicting paths. Every `internal` failure is logged with its detail and answered with the message `internal error` and no other `data` keys, so no internal detail, credential or git stderr reaches the agent.

## Role profile templates

Creating a project seeds four profiles instead of one blank agent — `claude`, `planner`, `implementer` and `reviewer` — so a board has someone for each of its queues from the first minute, and a person who just wants a Claude Code session in the project has one to launch (ADR 0038, 0051). `claude` is the default: conversational, serving no state — serving `ready` would show it the implementer's queue — and asking for no git tool; the task tools are served to it like to every session. `implementer` and `reviewer` are `ephemeral` with `auto_launch` on, so the dispatcher puts them on the work in `ready` and `review` by itself ("Automatic dispatch"). They are seeded that way unconditionally, whether or not an agent credential exists at `global` or `project` scope: the dispatcher checks for one at launch and passes a profile over without one, so they start working once one is stored. Saving an edit to either of them without such a credential is the ordinary 400 of the auto-launch rule ("Agent profiles"), which switching `auto_launch` off avoids. The fourth queue, `merge`, is the orchestrator's: a new project's `merge` state is seeded with `auto_merge` on and `ready` as its conflict state, so approved work is merged without an agent ("Automatic merge"; ADR 0045). The seeded profiles are ordinary profiles: everything under "Agent profiles" applies to them, they can be edited, renamed and — apart from the default — deleted, and nothing reads the templates again after creation. They are also offered when a profile is created, through `GET /profile-templates` ("Agent profiles"), which is how a project that predates the seeding gets the roles and how a deleted one comes back.

The endpoint offers three further templates that creation does **not** seed, and a **seeded** column says which is which. `merger` is a queue role a person launches, but the state it serves is merged by the orchestrator in a new project, so seeding it would put an agent on a queue nothing waits in; a project that turns `auto_merge` off on `merge` and wants an agent there creates one from this template (ADR 0045). `tech-debt-scanner` carries a schedule, and a schedule spends money on a cadence nobody asked for — whether or not there is any work — so turning one on is a decision a person makes (ADR 0038). Auto-launch differs in kind: it only ever starts work somebody queued, which is why the implementer and the reviewer are seeded with it (ADR 0051). `resolver` is a helper a person launches for one conflicting merge; it serves no queue and takes no task, so a copy in every project would be a profile nothing ever launches by itself.

| Profile | `kind` | `serves_states` | `mcp_tools` | `schedule_cron` | `auto_launch` | `is_default` | seeded |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `claude` | `conversational` | — | — | — | no | yes | yes |
| `planner` | `conversational` | `backlog` | — | — | no | no | yes |
| `implementer` | `ephemeral` | `ready` | — | — | yes | no | yes |
| `reviewer` | `ephemeral` | `review` | `list_session_branches` | — | yes | no | yes |
| `merger` | `conversational` | `merge` | `list_session_branches`, `merge` | — | no | no | no |
| `tech-debt-scanner` | `ephemeral` | `ready` | — | `0 4 * * *` | no | no | no |
| `resolver` | `conversational` | — | — | — | no | no | no |

Every other field is the documented default of "Agent profiles": `claude` as the backend, `bypass`, `SESSION_IMAGE_DEFAULT`, no model, no runtime, no secrets, 1800 seconds, a `max_concurrent` of 1, and partial messages at the kind's own default — on for `claude` and `planner`, off for `implementer` and `reviewer`. `GET /projects/{pid}/profiles` of a new project returns exactly the four seeded ones, oldest first, in the order of the table: the default first, then the roles in the order a task travels through them.

`push` is granted to nobody: only the orchestrator reaches the upstream remote (ADR 0007). `rebase` is granted to nobody either. The merger must not have it, because an approval is bound to the commit that was reviewed (ADR 0018) and a rebase would produce a commit nobody reviewed — a merge that conflicts goes back to `ready` instead. The implementer does not need it, because its work clone's `origin` is the project repository and it can fetch and rebase there itself (`ARCHITECTURE.md`, "Git model").

The prompts are **copied** into the project's own rows, not referenced: editing one changes that project only, and upgrading Mars never changes an existing project's agents. They name the seeded task states (`backlog`, `ready`, `review`, `merge`, `done`), which a project may later rename or delete. Renaming a state keeps the profile serving it, since `profile_states` links by id, but the prompt then names a state that no longer exists and needs a manual edit; deleting a state follows "Task states" — it is refused while any task is in it, and otherwise the link goes with it and the profile simply serves one state fewer.

The four roles that build or check code — `implementer`, `reviewer`, `merger` and `resolver` — carry one further paragraph about the session container: it is disposable and the agent's own, a missing toolchain is installed rather than reported as a blocker, there is no root so installs are user-level, what needs root or a system library is said in a comment, a hand-off or the conversation instead, and nothing installed is committed (`ARCHITECTURE.md`, "Session container specification"). It names no image and no tool as present, since a profile's image is editable; tools appear only as examples of how to install. `planner` and `tech-debt-scanner` do not carry it, because they build nothing: one plans and the other reads. Nor does `claude`, whose prompt stays short because what the session does is up to the person it talks to.

**`tech-debt-scanner`** is the first scheduled template (`ARCHITECTURE.md`, "Scheduled agents"): a daily scan that reads the code and files tasks for the debt it finds. It is `ephemeral` because only an ephemeral profile may carry a schedule, and `0 4 * * *` is once a day at 04:00 UTC, which the user is expected to move to whatever hour suits their project. Its `schedule_prompt` is what each run is given as its `message`, the way `system_prompt` says who the agent is; both texts are below. It asks for no git tool, because filing a task needs none: the task tools are served to every session. It serves `ready` — the state a new project's unplanned work goes to — because `ready` is the one tool that lists tasks and lists only the calling profile's served states, so a scanner that served nothing could not see what it filed yesterday and would file it again today; a project whose unplanned work goes elsewhere renames that in the profile, as it does for any other role. Creating a profile from this template is the ordinary `POST /projects/{pid}/profiles`, so the schedule's credential rule applies to it like any other: without the backend's agent credential at `global` or `project` scope the create is the documented 400 and the profile is not made ("Scheduled profiles").

**`resolver`** resolves one merge that conflicted. A person launches it from the merge's **target**, so its working tree starts there, and the first message names the **source** ref, the commit it should point at, and the paths that conflicted. It fetches the source from its clone's `origin` with an explicit refspec — `refs/sessions/<session id>` for a session branch, `refs/handoffs/<hand-off id>` for a hand-off, an ordinary branch of `origin` for an integration head — checks that the fetched tip is the named commit, merges it with `git merge` rather than a rebase so the source commit keeps its id, resolves the conflicts, runs the project's checks and commits on its own session branch. It never merges into the target and never pushes: that branch contains the source commit and the resolution, so it merges cleanly into the target, and a person merges it like any other session branch. That is why it asks for no git tool. It is `conversational` and serves no state because it takes no task: a conflict it cannot decide from the code and the documents is asked of the person in the conversation, not escalated with `needs_human`. It carries the default image and permission mode, like `claude`.

The texts below are the templates verbatim; `orchestrator/src/projects/templates/<name>.md` holds each system prompt, `<name>.schedule.md` each schedule prompt, and a test compares them with this document, as it does for the tool descriptions above.

## Frontend

Vite, React 19, TypeScript strict, Tailwind CSS 4, React Router 7, TanStack Query, Zustand for per-session and per-project reducers, `@tanstack/react-virtual` for the transcript, `react-markdown` with `remark-gfm` for text and `lowlight` for highlighted code fences, a diff renderer for edit tools, `xterm.js` for the terminal view, Playwright for end-to-end tests.

Structure:

```
frontend/src/
├── components/     reusable UI: FieldShell, FormField, SubmitButton, Alert, QueryErrorAlert, LoadingState, EmptyState, HelpLink, PageLayout, AuthLayout, ProtectedRoute, AdminRoute, ...
├── pages/          route-level: LoginPage, AcceptInvitePage, ChangePasswordPage, ForgotPasswordPage, ResetPasswordPage, DashboardPage, ProjectsPage, ProjectPage, SessionPage, SecretsPage, SettingsPage, AdminPage (users + invites); pages/project/ holds ProjectPage's tab panels, among them ProfilesTab and the ProfileEditor panel it opens
├── session/        SessionView, Transcript, Composer, TerminalView, tool renderers, sessionStore (Zustand), useSessionSocket
├── tasks/          TaskBoard, TaskCard, TaskDetail, TaskStatesEditor, taskStore (Zustand), useTaskStream
├── help/           the help page's topics (HELP_TOPICS, helpPath) and one Markdown file of prose per topic
├── launch/         what both launch forms are built from: useLaunchSession, ProfileSelect, BaseRefSelect, the hand-off base note
├── services/       apiClient (fetch wrapper with refresh-on-401), errorMessage (the one error-to-text rule), queryKeys and queryOptions (the keys, and the reads more than one view makes), auth, currentUser (the one `GET /users/me` install), projects, profiles, sessions, tasks, taskStates, secrets, users, git
├── hooks/          useAuth, useFormSubmit
├── types/          TypeScript mirrors of every API shape in this document
└── utils/
```

Rules: components never call `fetch`; every request goes through `services/`. A read that more than one view makes is defined once, as a `queryOptions` factory beside its key in `services/queryOptions.ts` — the project, its refs, its profiles and its sessions are four of them — so two views reading one key cannot disagree about what the answer is; a call site adds only what is genuinely its own, an `enabled`, a placeholder or a poll that belongs to that screen, by spreading the factory. Auth state lives in `services/auth` with an in-memory access token mirrored to `localStorage`, and a `useAuth()` hook that subscribes to it. `ProtectedRoute` redirects a user whose current `must_change_password` is set to the change-password page. Token role/flag snapshots are UI hints only; the backend always checks the current user. Load `GET /users/me` at authenticated startup and refresh the current user after an authorization 403 so a demotion updates admin navigation. That user lives in `services/auth` and nowhere else: a read of `GET /users/me` installs what it answered — the startup one directly, the 403 refresh and the settings page through `refreshCurrentUser` in `services/currentUser` — and every component, the settings page included, reads it back through `useAuth()`. No page keeps a second copy in the query cache and writes it back into the store, which is what would give a user demoted elsewhere their admin navigation back from a cached answer. A failed refresh with 401 clears the access token from memory and `localStorage`, clears authenticated query and stream stores, closes streams and returns to login. Self-service password changes replace the token pair and reconnect streams without replaying pending inputs; installing a rotated pair is not such a replacement and reconnects nothing, so an open session socket, its exec terminal and the task stream survive every ordinary token rotation. `services/auth` owns the one in-flight refresh of the whole frontend — the HTTP client's 401 retry, the session WebSocket and the task SSE stream all await the same rotation, because the refresh cookie is single-use and a second submission of it fails and clears the cookie. A 401 whose request carried a token that is no longer the current one retries with the current token instead of rotating again. Each rotation is tied to the authentication generation it was started for: a completion that no longer owns the browser's authentication installs nothing and signs nobody out — it answers its callers with the credentials that replaced it, so they reconnect exactly once, or, when the user is signed out, fails them without a retry. The tabs of one browser share that storage key and follow it: `services/auth` listens for `storage` events on it, a removed value signs this tab out locally — the same handler path as its own sign-out, without a second `POST /auth/logout` — and a different value is adopted as this tab's access token, as a rotation or as a replacement by the rule above. The rotation is serialised across tabs as well as within one, under a `navigator.locks` request where the browser has the Web Locks API; inside the lock the stored token is read again and a token another tab has already installed is adopted instead of submitting the single-use cookie a second time, so two tabs whose tokens expire together produce one rotation and no signed-out loser. A browser without the Web Locks API rotates per tab as before. Signing out is local first: the token, the stores and the streams go when the user presses the button, and the cookie-revoking request follows under an `AbortSignal.timeout`, so an unreachable orchestrator cannot leave a browser signed in. A sign-out whose reason is a failed refresh carries the current location to `/login` as the return destination, exactly as `ProtectedRoute` does, so an expired session returns to the task or session it was on after signing in again ("Copy links"); a deliberate sign-out carries none. Reads that can be abandoned pass TanStack Query's cancellation signal to the service function — the session-head diff and the transcript history page at least — so a superseded query is cancelled on the wire and not merely ignored.

Routes: `/login`, `/invite/:token`, `/change-password`, `/forgot-password`, `/reset-password/:token`, `/` (DashboardPage), `/projects`, `/projects/:id` (ProjectPage, with tabs for sessions, board, branches, profiles, shared directories, states and secrets), `/projects/:id/tasks/:number` (the board with that task's drawer open), `/sessions/:id`, `/secrets`, `/settings` (own password and `notify_email`), `/help` (HelpPage, one section per help topic), `/admin`. The project page's tab is the `?tab=` search parameter — `sessions` (the default), `board`, `branches`, `profiles`, `shared-dirs`, `states`, `secrets`, with an unknown value falling back to `sessions` — and `/projects/:id/tasks/:number` is the board tab with that task's drawer open.

**Read failures.** A query keeps its last good data through a failed refetch, so a view that has data keeps rendering it and shows the failure as a non-blocking `QueryErrorAlert` above it — the shared "message plus `Try again`" banner, whose text each caller words itself. The blocking form of the same banner is only for a query with nothing to show: a first read that failed, or one whose answer is a refusal, in which case it carries no retry. A failed read is never an empty result: `EmptyState`, and every derived claim about what a list does not contain — a served state that is not a queue state, a declared secret that does not exist yet, the task counts behind a state's delete button — renders only when its source query succeeded, and that query's failure is shown with a retry instead. The retry policy is one place, `queryClient.ts`: an `ApiError` below 500 is an answer and is never retried; a network failure or a 5xx is retried once, which absorbs the single 502 of a restarting orchestrator. Call sites do not override it.

**Failure messages.** One function turns a caught failure into the sentence a user reads: `errorMessage(caught, fallback?)` in `services/errorMessage.ts`. An `ApiError` that carries words is shown in the server's own words, whatever the status — this document phrases the refusals, and 5xx bodies are generic by `CLAUDE.md` rule 3, so there is nothing to hide and nothing to improve on. An `ApiError` that carries none — a reverse proxy's HTML, an empty body — is named by its status instead: `Orchestrator unreachable` for 502, 503 and 504, `HTTP <status>` for anything else. `Response.statusText` is never that text: it is always empty under HTTP/2 and HTTP/3, so `apiClient` gives a body-less response the same status wording rather than an empty `error`, and no alert ever renders blank. A network failure — the `TypeError` `fetch` rejects with — reads `Orchestrator unreachable`; anything else is a bug in the frontend and reads as the caller's fallback. A feature helper adds only its own special cases and delegates the rest here, and no page forges an `ApiError` to carry its own wording: `useFormSubmit(action, { mapError })` takes the form's reading of a failure, and a failure that the client itself decided the words for is a `MessageError`. The function is pure and safe to call from render; the failure is logged once where it is caught, by `logUnexpected`, never by a formatter called while an alert is on screen.

Four readings are keyed on the orchestrator's prose rather than on a status, because the status alone cannot separate them, and a reword of the backend message silently changes the frontend: `POST /auth/reset-password` answers 400 both for a token that is unknown, used or expired (`invalid or expired token`, which sends the visitor back to request a new link) and for a password that breaks a rule; `POST /users/{id}/password` answers 400 both for `current password is incorrect` — which is the field's refusal and not the form's, so it is shown on the current-password field, clears that one field and leaves the new pair the user typed alone, while any other refusal of the same call clears the new pair and keeps the current password — and for a new password that breaks a rule; a shared-directory create answers 409 both for a duplicate name and for a duplicate path, which the form tells apart to decide which field the refusal belongs beside; and a secret create or rename answers 409 both for a name the scope already has (`secret already exists`, reworded into a sentence naming the scope) and for an agent credential the scope already holds ("Secrets"), which is shown as the server wrote it because it names the credential in the way and what to do about it — everywhere the secrets manager and the agent-credential section show it, a body the frontend does not recognise falls back to the server's own words.

**Code splitting.** The entry bundle carries only what a first paint needs: the route table, the auth pages and the dashboard. `/projects`, `/projects/:id`, `/sessions/:id`, `/secrets`, `/settings`, `/help` and `/admin` are `React.lazy` imports of their own page file — never of the `pages/` barrel, which would defeat the split — behind one `Suspense` in `App.tsx` whose fallback is `LoadingState` inside `PageLayout`. Within the session view the `Terminal` panel is lazy too, so `xterm.js` and its stylesheet are fetched only when that tab is first opened; `SidePanel` renders the active panel inside a `Suspense`. The syntax highlighter behind `MarkdownBody`'s code fences splits the same way but without a boundary: `CodeBlock` reaches `components/highlight.ts` through a dynamic `import()`, so `lowlight` and its language definitions are a chunk of their own, fetched the first time a reader is shown a fence with a language, and the entry chunk carries neither them nor `CodeBlock`'s path into them. There is no `components/` barrel, and no `services/`, `utils/`, `tasks/` or `pages/` one either: a barrel over a feature directory is a static edge to every module in it, and on the first-paint path that is how feature UI ends up preloaded beside the login form (`ARCHITECTURE.md`, "Frontend architecture", Barrels and the first-paint path). `npm run build` therefore emits one chunk per lazily loaded route and no chunk-size warning, and then runs `scripts/check-entry-chunk.mjs`, which fails the build if the chunks a first paint fetches contain a marker string of the secrets, git or task-board UI, or exceed the first-paint byte budget.

**Secrets page.** The scope `SecretsPage` shows lives in the `?scope=&scope_id=` search parameters, so a reload keeps it and a link carries it. Two spellings are normalised to the one the page can show, while deciding what to render and before any read is made, and the URL is corrected to match: a user scope naming the caller is `My secrets` with no `scope_id` ("Secrets": a user scope with no `scope_id` is the caller's own), and another user's scope in the hands of a non-administrator — a pasted link, a stale bookmark — is the caller's own too, since only an administrator may select another user and reading on would only reach a 403 with no scope selected in the picker. Under the scope picker a hint says what each scope can reach — global secrets every project's sessions, project secrets only that project's, user secrets only the sessions their owner launches — and every secrets list, here and on a project's secrets tab, is headed by the resolution rule of `ARCHITECTURE.md`, "Secrets" (a secret other than an agent credential reaches a session only when the session's profile lists its name; the launching user's scope overrides the project's, which overrides global; an orchestrator-only secret is never injected) with a link to the `secrets` help topic. The create form's name field states the name rule and its `Orchestrator only` box carries the flag's meaning as visible text; a row with the flag set shows `never injected` beside its lock rather than in a tooltip; and a project's `GIT_CREDENTIAL` row says it is used by git operations, should be replaced when the token expires and kept orchestrator-only, and links `git-credential`.

**Agent credentials.** `SecretsPage` opens with an `Agent credentials` section above the general list. It lists the secrets whose `credential_for` is set, each under its label rather than its name (`Claude subscription token` for `CLAUDE_CODE_OAUTH_TOKEN`, `Anthropic API key` for `ANTHROPIC_API_KEY`) with the scope it applies to and its last use, and the general list leaves them out. The scopes it reads are the ones a launch resolves over — the caller's own user scope (`You`), every project (its name) and `global` (`Everyone`) — not the one scope the picker below has selected, so "is there a credential at all" is answered wherever the page is pointed; an administrator who has selected another user's scope sees that scope too, under that user's username. Each row offers the same value replacement and deletion as an ordinary secret, and no rename: the name is the credential. With no credential at any of those scopes the section shows, in the warning colour, that sessions cannot authenticate without one. `Add agent credential` is a form of three fields: the kind (the subscription token carries the hint that `claude setup-token` prints it and needs a Pro or Max subscription, the API key that it is created in the Anthropic Console and billed per use), the value (a password-type field, cleared once it is stored), and `Applies to` — `Me` (the default), one project chosen from a select, or `Everyone`, under a hint that a person's own launches use the most specific credential that applies while automatic and scheduled runs, having no user, need a project or `Everyone` credential (`ARCHITECTURE.md`, "Task tracker" → "Unattended launches") — which become `scope` and `scope_id` of an ordinary `POST /secrets`; the name is never typed and there is no orchestrator-only control. `A project` is disabled, with the reason, when there are no projects. A 409 is shown with the body's `error`, which names the credential already there. The labels, hints and names are a constant table per backend in `src/secrets/`, the one place the frontend knows them. The section's header and the `Applies to` hint link the `agent-credentials` help topic.

`AgentCredentialNotice` renders one entry of `GET /projects/{pid}/agent-credentials` (TanStack Query key `["projects", pid, "agent-credentials"]`, invalidated by every secrets mutation) for the backend of the profile at hand: `Authenticates with your Claude subscription token`, `… the project's Anthropic API key`, `… the shared …`, or, in the warning colour, `No agent credential: sessions of this profile will fail to authenticate` with a link to `/secrets`. The answer is per caller and nothing about it is stored on the profile, so a teammate opening the same profile reads their own credential.

**Role templates.** Creating a profile can start from one of the roles of "Role profile templates" instead of from nothing. `ProfileEditor` shows a `Start from` select — `Blank` and one entry per template of `GET /profile-templates` (TanStack Query key `["profile-templates"]`, read once per build with an unbounded `staleTime`, since the templates are compiled into the orchestrator) — and only when creating: editing an existing profile has nothing to start from. Nothing is created until the user saves, through the ordinary `POST /projects/{pid}/profiles`, so the pre-fill is an editable starting point and not an instantiation. `is_default` is never applied by this flow.

Two adjustments make the pre-fill savable in any project. The template's name is suffixed to the first free `<name>-2`, `<name>-3`, … when the project already has a profile of that name, because names are unique within a project and are what the launch form shows. And a served state the project has no `queue` state for is dropped, with an inline note under the select naming what was left off, rather than being sent and refused with the 400 of "Agent profiles"; while the project's own state list has not arrived the template's states are kept and the served-states fieldset flags each unknown one as it does for a stored profile. Switching the selection after a field has been typed asks first. If the template request fails the select holds `Blank` alone and the editor behaves exactly as it does without templates.

**Unattended launches.** What the dispatcher may do is one subject spread over a project and its profiles, and it is headed `Unattended launches` in both places (`ARCHITECTURE.md`, "Task tracker" → "Unattended launches").

`ProfileEditor` shows a fieldset with the `auto_launch` toggle and the `max_concurrent` field, and shows it only while the form's kind is `ephemeral`: the other kind cannot carry the flag, so switching to it takes the controls away and the submitted body carries `auto_launch: false` whatever the checkbox last held, while the form keeps the tick so switching back restores it. Ticking the toggle while the project's agent-credential answer — the one `AgentCredentialNotice` already reads, not a second request — says there is no credential, or only a `user`-scope one, shows in the warning colour that an unattended launch has no user to resolve one for, with a link to `/secrets`; an answer that has not arrived or failed says nothing and the save decides. The three 400s of "Agent profiles" land where they are about: `auto_launch requires this backend's agent credential at global or project scope` and `auto_launch requires an ephemeral profile` are shown at the toggle in the server's own words, with the same pointer to where a project or global credential is set up and the other way out, unticking the toggle to save without unattended launches — the one a seeded or template-made `implementer` or `reviewer` needs before a credential exists — and `max_concurrent must be at least 1` is refused by the field before it is sent.

**Scheduled profiles.** The same fieldset pattern carries the schedule of "Agent profiles" → "Scheduled profiles", under the same ephemeral-only rule and for the same reason: a scheduled run has nobody behind it. `ProfileEditor` shows a `Schedule` fieldset while the form's kind is `ephemeral`, owned by a *Run this profile on a schedule* checkbox: while it is off the two fields below it are disabled and nothing is sent, so a schedule is switched off by unticking it, never by emptying a box. The checkbox starts on exactly when the stored profile, or the template the form was filled from, has a schedule. Both fields are sent on every save, `null` and `null` — the checkbox off, or the other kind — being how a schedule is cleared, whatever the boxes last held, while the form keeps what was typed so ticking the box or switching back restores it.

No cron parser ships in the bundle: whether an expression is valid, and when it next fires, are the server's answers alone (ADR 0043). The form states only the one rule it can state without knowing cron — with the checkbox on, both fields are required — and every 400 of "Scheduled profiles" is shown in the server's own words on the field its leading token names, `schedule_cron …` on the expression (the 5-field rule, the parser's detail, the kind, the credential) and `schedule_prompt …` or `schedule prompt …` on the prompt, the way the `auto_launch` refusals are routed to their toggle. They describe what is saved, not what is being typed, because the server recomputes the next run on every read.

The profiles list carries an `Automation` column, so what runs without a person is visible without opening each editor: an `auto-launch` chip for the flag, a `schedule` chip whose tooltip carries the expression and the next run, and `manual` for a profile nothing launches by itself. The editor's hints say what each field does to a session, and two of them follow the form: the idle timeout's says that a conversational session is parked and an ephemeral one failed as `stalled` (`ARCHITECTURE.md`, "Stop semantics"), and the served states' says what the agent's `ready` tool offers or, on an ephemeral profile with `auto_launch`, what the dispatcher launches for. Each git tool's checkbox carries one line on what granting it allows ("MCP tool contracts").

The project settings form carries the project's half: a nullable session cap, empty meaning no cap, and an `automation_paused` toggle, under the same heading and the note that both hold automation back only. An emptied cap is sent as an explicit `"max_concurrent_sessions": null`, since omitting the key would leave the stored one alone. The project header shows the cap beside `max attempts`, and while the project is paused it shows `automation paused` in the parked colour next to the status pill — the one state on that strip, and the only thing on it that takes colour.

**Launch source.** A session whose `launch_source` is not `user` carries a tag saying so — `dispatcher`, `schedule` — beside its name in the project's session list and in the session header, wherever the launching user would otherwise be named. **Confirmations.** A destructive or overwriting action asks in place, in one inline `ConfirmPanel`: the tone of what it is about to do, a sentence naming the thing, a way out, and a confirming button whose label names its target (`Delete user ada`, `Remove target`, `Move to done`) so a table of rows offering the same verb has one button per row and a screen reader hears which. In a table the panel opens in a row spanning the table, under the row it was pressed on; inside the task drawer it registers its own cancel with the drawer's Escape registry, so Escape withdraws the confirmation before it closes the drawer ("Task board"). The panel keeps no state: what it shows as pending and as refused is the `useMutation` or `useFormSubmit` that owns the write. Tasks it filed will not be dispatched until they are merged.` with a link that opens the header's branch panel, where they can be merged — again a warning and never a refusal. **Session state.** `useSessionSocket(sessionId)` opens the WebSocket with `after = store.lastSeq`, reconnects itself on close under the bounded rules of "Authentication", fetches older history through REST when the user scrolls up — pages of 200 events, the first page and every older one alike, a build-time constant a build may override with `VITE_SESSION_HISTORY_PAGE_SIZE` (1 to 500; only the end-to-end dev server does, `frontend/tests/README.md`), since `limit` is the client's to choose — and dispatches every event to the session store. The store never keeps the event list; it folds events into:

```ts
interface SessionState {
  session: Session | null;
  status: "connecting" | "live" | "reconnecting" | "offline";
  connectionError: string | null;          // why it gave up; null unless status is "offline"
  lastSeq: number;
  order: string[];                         // message ids in display order
  messages: Record<string, Message>;       // id -> folded message
  pendingTools: Record<string, string>;    // tool_use_id -> message id awaiting a result
  toolIndex: Record<string, string>;       // tool_use_id -> message id, kept after the result lands
  subagents: Record<string, string[]>;     // parent_tool_use_id -> message ids nested under it
  oldestSeq: number | null;                // lowest seq held: the `?before=` cursor for older history
  hasMore: boolean;                        // older history remains behind oldestSeq
  historyStatus: "idle" | "loading" | "error";  // where the request for the page before oldestSeq stands
  historyError: string | null;             // why that request failed; null unless historyStatus is "error"
  gitEventSeq: number;                     // seq of the last `git` event; the Changes panel refreshes on it
  streamEndSeq: number;                    // seq of the first event held that closed the streamed blocks: a `result`, a fatal `error` or an ended `state_change`
  turnActive: boolean;                     // a turn is in progress: the composer's button reads "Interject"
  lastRejection: { client_id: string; reason: string } | null;  // latest `input_rejected`, cleared by the next send
}

type Delivery =                            // how far a message the user sent has got
  | { state: "pending" }                   // optimistic: sent, with no answer of any kind yet
  | { state: "accepted"; seq?: number }     // `input_accepted` (or the REST 202), at the seq the echo will carry
  | { state: "confirmed" }                 // its own `user_message` event arrived
  | { state: "rejected"; reason: string }; // refused, or lost with the connection: resendable

type Message =
  | { id; kind: "user"; text; delivery: Delivery }
  | { id; kind: "assistant_text"; text; streaming: boolean; interrupted?: boolean }
  | { id; kind: "thinking"; text; redacted: boolean }
  | { id; kind: "tool"; tool_use_id; name; input; result?; is_error?; truncated?; running: boolean;
      children?: string[]; subagent?: { description; agent_type?; is_error? } }
  | { id; kind: "system"; text; level: "info" | "warn" | "error"; detail?: unknown }
  | { id; kind: "result"; subtype; is_error; num_turns; duration_ms; cost_usd?; usage? }
  | { id; kind: "raw"; native: unknown };
```

`text_delta` appends to the current streaming assistant message; the following `text` replaces it and clears `streaming`. One text block is always exactly one assistant message: a row that the agent did not write — a user message (the "Interject" of a running turn, optimistic or confirmed), a system row from a `git`, `launch_warning`, `state_change` or socket error, a `raw` line — may land in the middle of a delta run without ending the block, so the fold looks past it and the block keeps its place above it, while a tool, thinking, a `result` or a completed text block does end it and the next delta starts a new message. The streamed blocks are closed, and `streamEndSeq` recorded, by whatever ends the turn: a `result`, a fatal `error`, or a `state_change` into `parked`, `done` or `failed` — a kill or a park mid-stream produces no `result`, and the cursor must not go on blinking. A block closed without its completing `text` is marked `interrupted`, because its text is the deltas that arrived and not the whole block. When an older page's boundary falls inside a delta run, its fragment and the live half of the same block are merged into one message at the older position, as a split tool is: a live half still streaming, or one an interruption closed, contributes the deltas after the cut, while one completed by `text` contributes the whole block and replaces the fragment. Which live message is that same block is decided by `streamEndSeq`: the first close the live half holds is the fragment's own block ending, so a live message above it continues the fragment and one below it — the block of the turn after a park and its resume, with only transparent system and user rows between — is left alone, the fragment stopping at what it had. Every delta is folded as it arrives — the store holds one string per message and never a queue — and the throttling a growing message needs lives in the renderer ("Markdown"), not in the fold. `tool_call` creates a tool message and registers it in `pendingTools`; `tool_result` completes it and removes it from `pendingTools`. Every tool message the fold places is also registered in `toolIndex`, which keeps its entry after the result lands, so finding the message a `tool_use_id` belongs to — including finding that there is none yet, which is what every `tool_call` asks — is a lookup rather than a walk of the whole transcript. Events carrying `parent_tool_use_id` are placed under the tool message with that id instead of at the top level. `user_message` with a `client_id` matching an optimistic message replaces it, keeping its place in `order`. How far a message the user sent has got is the single `delivery` field, so "pending and rejected at once" cannot be written down: it starts `pending`, becomes `accepted` when the orchestrator answers `input_accepted` — or the REST fallback's 202 — becomes `confirmed` when its own `user_message` event arrives, and becomes `rejected`, carrying the reason, when the input is refused. Acceptance is not delivery (ADR 0020), and neither is a socket that still reads as open: so whenever the connection ends — a close, a give-up into `offline`, a sign-out, a reconnect, the page going away — every send still `pending` is marked `rejected` and offered for resending, while an `accepted` one is left alone because the orchestrator has it and a reconnect replays its echo. That marking is the message's own; it is not an `input_rejected`, so it neither raises the composer's banner nor restores the text into the box. Event-derived messages have the id `e<seq>` and an optimistic one `client:<client_id>`. A `tool_result` whose `tool_call` has not been seen becomes a tool message named `unknown`, and a subagent event whose parent has not been seen hangs under a placeholder tool message named `Agent` with the id `tool:<tool_use_id>`, so nothing is dropped; when an older history page later supplies the real `tool_call`, the two halves are reconciled into one message at the older position, so one `tool_use_id` is always one message. Asking for an older page is a request with a status of its own: `historyStatus` is `loading` only while one is really in flight, `idle` once it has landed and `error` when it failed, with the reason in `historyError`; a failure keeps everything already folded and loses only the page that did not arrive. Simultaneous askers — a scroll gesture and the fill rule of "Transcript rendering" — share one request rather than fetching the same cursor twice, and `loadOlder` resolves `false` when it failed. The failure releases the transcript's duplicate-request guard so that cursor can be asked for again, but only the reader's Retry asks: the automatic paths stop at `error` instead of retrying into the same failure. Older pages are folded on their own and prepended; `lastSeq` only ever moves forward and an event at or below it is ignored, which is what makes reconnect replay idempotent. A message the client itself has to show, such as a socket `error` frame, is appended as a `system` message with a `local:<n>` id and touches no cursor. The connection has a status of its own, and it never promises more than it is doing: `reconnecting` means an attempt is pending — a retry timer, the rotation an authentication close is worth, or the REST read that both settles an expired token and tells a deleted or forbidden session from a refused stream — while `offline` means none is, `connectionError` is the sentence saying why, and the view shows it above the transcript with a `Reconnect` action that starts the schedule from the beginning. The four readings that end there are the session deleted, the session no longer this user's, this browser signed out, and a stream refused although the session still reads over REST with the same credentials — which is a refusal of the stream and not of the user, so nobody is signed out for it — plus the bound on attempts that never open, under the rules of "Authentication". The composer is unaffected by either: a socket that is not `live` sends over REST, as it does while reconnecting.

**Session store lifecycle.** There is one store per session id, held by a registry rather than by the page that opened it, so returning to a session resumes from the transcript already folded instead of fetching it again. `useSessionSocket` is that store's owner for the lifetime of its connection and lets go of it when the page unmounts; what it leaves behind keeps the transcript and the cursors but goes back to `connecting`, because the `status` and `connectionError` of a connection that has ended describe nothing the next visit is doing — a kept `live` would have the next visit's header claim a stream that does not exist and its terminal attach to a socket that has not opened. On that next visit the fresher of the two readings of the session is what the header shows and what the store is seeded with, decided by `last_seq` and then `last_activity_at`: a retained store is ahead of the page's REST read only while its own connection is keeping it current, and the socket's first `session` frame may be seconds away or never arrive. A store nobody owns is kept for a return visit under a bound — at most three, the least recently used going first — because a folded transcript is the one unbounded thing the frontend holds in memory; a store in use is never evicted, however many other sessions are opened beside it, and a deleted session's store is dropped outright rather than kept for a return that cannot happen. Signing out clears them all: every store is reset, the unowned ones are dropped, and a generation counter moves on, which is what makes a history page, a first page or an input rejection still in flight discard its answer instead of folding one login's transcript into the next one's (ADR 0027: transcripts are unredacted, optimistic messages included). Every other change of principal in the same tab does the same — a login over an existing one, and a token another tab installed for a different account — while a self-service password change and an ordinary rotation are not changes of principal and keep what has been folded. State held per session beside the store — which transcript rows are expanded, and a refused message handed back to the composer to resend — is cleared with it.

**Markdown.** One component, `MarkdownBody`, sets every piece of written text in the application: assistant messages, task descriptions, task comments and hand-off comments. It renders GitHub-flavoured markdown in the browser from the text the API sends — no HTML crosses the API (ADR 0040) — and styles every element with the console tokens: a compact heading scale where weight and spacing carry the hierarchy, bordered compact tables honouring GFM column alignment inside a horizontally scrolling box so a wide table never widens its row, quoted blocks behind a muted left rule, monospace for inline and fenced code, nested list markers by depth, and read-only checkboxes for task lists. Long unbroken strings wrap; code does not. Links open in a new tab with `rel="noopener noreferrer"`, and `react-markdown`'s default `urlTransform` drops `javascript:` and similar schemes. Two things are not rendered. HTML in the text is inert — there is no `rehype-raw`, so a `<script>` or an `<img onerror=…>` in agent or user text is shown as text and never becomes an element (ADR 0027). Images are never loaded: `![alt](url)` renders as a link reading `[image: alt]`, because fetching a remote image from agent-written text would disclose the viewer's address and the timing of the session to whoever the agent was induced to name. The measure cap sits on the text blocks, so a table or a code fence may use the full width of the row it is in. Inside the transcript it also sets the other agent-written prose — thinking text and a subagent's final report — while user messages, tool results and the orchestrator's own strings stay literal ("Transcript rendering", below). A fenced block is a `CodeBlock`: a quiet header carrying the fence's language and a `Copy` action above the code in that bordered monospace box, `Copy` writing exactly the text between the fences — no header, no newline added and none dropped — showing `Copied` only once the clipboard write resolves and, when the clipboard refuses, selecting the code so it can still be copied by hand, the same rule `Copy link` follows. Fences are syntax-highlighted through `lowlight` over an explicit language set — rust, typescript and tsx, javascript, json, bash and shell, toml, yaml, sql, python, go, diff, html and xml, css, markdown and dockerfile, with the aliases those definitions declare (`rs`, `ts`, `sh`, `zsh`, `console`, `yml`, `md`, `patch`, …) — and over nothing else: there is no auto-detection, so a fence whose tag is unknown shows that tag and stays plain, as does a fence with no tag. The token colours are four low-chroma classes defined once in `src/index.css`, held clear of the state hues, so nothing inside a code block can be read as running, parked, failed or needing a human, and a diff fence's added and removed lines are told apart by brightness rather than by green and red. The highlighter is a lazy chunk (see "Code splitting"): a block paints immediately as plain text in the same `pre > code`, in the same font and at the same line height, and is upgraded in place when the chunk has arrived — no `Suspense` boundary, no fallback flash, no layout shift. It is asked only once the code has held still for a moment, so a fence still growing while a message streams is highlighted once rather than on every delta, and while it grows the spans already computed for its prefix are kept and the new tail is shown as plain text. A block above 2,000 lines or 200 KiB — a pasted log — is never highlighted. An assistant message that is still being written goes through `StreamingMarkdown`, which makes the cost of a `text_delta` proportional to the unfinished tail rather than to the message: the text is split at top-level block boundaries — a blank line outside a code fence, and only where what follows cannot change how what precedes it parses, so a loose list, a blockquote with a blank line in it, an indented continuation and anything inside a fence stay in one block — and every block but the last is rendered once and memoised, while only the last, growing block is parsed again. Deltas are coalesced to at most one render per animation frame, showing whatever has arrived when the frame runs; a completed message renders at once and through the same path, so the transcript's DOM is not rebuilt when streaming ends. Half-written constructs are left alone rather than guessed at: an unclosed fence is a code block from the fence to the end of the text, and a table whose delimiter row has not arrived is shown as the text it still is and becomes a table once, when that row arrives. Link reference and footnote definitions resolve against the whole document, which block-by-block rendering cannot do, so they resolve only when the message completes: while it streams such a reference is shown literally, and a completed message carrying a definition is rendered in one piece.

**Transcript rendering.** One renderer per tool family, chosen by tool name: markdown for assistant text (`MarkdownBody`, above); a side-by-side or unified diff for edit and write tools (computed from `old_string`/`new_string` or file content); monospace with ANSI stripping for shell tools; a one-line summary over the input and result for read, glob and grep tools; a nested, collapsible transcript for subagents; a JSON tree for anything else and for `raw`. The JSON tree is bounded the way the rest of the transcript is: a string above 500 characters is cut, and a branch draws its first 100 entries with the rest behind a "N more entries" action, so a tool result that is a ten-thousand-element array mounts a hundred rows and not ten thousand. Every tool row starts collapsed to its header — the tool's name, one line saying what it was asked (the shell command's description or first line, the file path, the search pattern) and its status — and a subagent's nested transcript starts collapsed whether the subagent is running or has ended, the header's status saying which; one click opens a row's full body, result included. A subagent's tool call is drawn as that nested transcript from the moment its `subagent_start` says it is one; before that event no tool family claims it, so the call shows its input and result as a JSON tree like any other tool rather than an empty group. Every fold of a row is the same control, and what the reader opened is held per session and keyed by message id, outside the row: the list is virtualised, so a row a few screens away is unmounted and anything kept inside it would be lost — the reader would come back to a subagent they were following collapsed, and to a layout that jumps, because the virtualizer's measurement cache is keyed by that same id and still holds the open row's height. It is cleared with the session store ("Session store lifecycle"), and a folded body is not rendered at all, so opening a row is what parses its markdown. A failed call keeps its failed colouring while collapsed. Long tool results are collapsed above 40 lines, counted as an editor counts them: the newline that ends the last line is a terminator and not a line of its own. The list is virtualised and follows the tail: it stays on the newest row as events arrive and as the virtualizer corrects its own height estimates, and stops following only when the reader moves the viewport upwards, which reveals a "Jump to latest" control carrying the number of top-level messages appended since, and re-follows when the reader returns to within 48 px of the bottom or presses that control. Two things that are not other people's messages never reach that number: an id that is no longer in `order` counts as no growth at all, because the one thing that removes one is the optimistic message being renamed in place by its own event, and the reader's own send re-follows the tail instead of being counted — they wrote it, so the view goes to it however far up they had scrolled. Older history is asked for when the reader comes within 200 px of the top, and also — because a page of 200 events can fold into a row or two, leaving a transcript that never overflows and so never fires a `scroll` event — whenever the content does not exceed the viewport by that margin, one page at a time until it does or there is none left. A band above the list says which of the two the request is in: "Loading earlier messages" only while one is running ("Session state", `historyStatus`), and a failed one replaced by the reason and a `Retry` action, the transcript underneath it unchanged. A page that lands keeps the reader on the row they were reading rather than the offset it moved. A row renders from its own message alone: it subscribes to `messages[id]` and is memoised on what it is handed, so a `text_delta` that grows one message re-renders that row and no other, however many rows the viewport holds, and the expensive parts of a row — the markdown parse and an edit tool's line alignment — are computed once per text rather than once per render. What is rendered as markdown is what an agent wrote as prose: assistant text, thinking text — inside its muted, italic, left-bordered fold, the muted tone carrying through headings and code — and a subagent's final report, shown in the subagent row's body rather than as monospace output, capped in height and scrolling instead of collapsed by a line count, and parsed only once the collapsed row is opened; a subagent result that is not text keeps the JSON tree. Everything else stays literal: a user message is shown `whitespace-pre-wrap` exactly as typed, so pasted code, underscores and asterisks are never reinterpreted; the results of ordinary and MCP tools stay monospace or a JSON tree, being program output and not prose; and `system` and `result` messages stay plain text, being short orchestrator- or CLI-generated strings.

**Session side panel.** The column beside the transcript holds one panel at a time — `Changes`, `Tasks`, `Terminal`, in that order — as an ARIA tab list: arrow keys, `Home` and `End` move and select, one tab stop rovers with the selection, and the panel names the tab that selected it. It opens beside the transcript on a screen at least 1024 px wide and starts collapsed to a rail below that; only the selected panel is mounted. Which tab is shown is derived, not remembered from the first render: it is the operator's own selection while that panel still applies, and otherwise the first panel that does apply. `Changes` does not apply to a `creating` session, which has no branch to diff, so a session launched from the UI opens on `Tasks` and moves to `Changes` the moment there is a branch. The `Terminal` is last for that reason: it is never the panel a session opens on, because showing it fetches the `xterm` chunk and, on a running session, opens a `/bin/bash -l` exec in the container — which happens when the operator selects it and at no other time. An attachment starts from a cleared exit bar, so a session that parks and runs again never shows the exit code of the shell that died with the previous container.

**Tasks panel.** `GET /sessions/{id}/tasks` is the session's whole tracker reading: the task it was launched for is one of the tasks it touched, since a launch claims the task and a claim writes the link. The panel therefore shows that task's row out of that list under `Launched for`, with whether the session still holds the lease, and lists the rest under `Touched` — each task once, and `Nothing beyond the task above.` when there is no rest. `GET /projects/{pid}/tasks/{id}` is read only when the list cannot answer. A `session` frame, which every lease taken or released writes, invalidates both readings rather than refetching them, so a session that was launched for no task asks for none.

**Changes panel.** The diff endpoint's internal fetch-back emits no separate `git` event, preventing a refresh loop; explicit sync actions still emit their outcome events. A tab beside the transcript fetches `GET /projects/{pid}/git/diff?head=<session id>` when opened and again on every `git` event, lists the files with their counts, and renders the patch with the same diff renderer as edit tools. An ended (`done` or `failed`) session that the project's `Branch` listing has no session ref for says so in one line above the diff — `No branch of its own: this session ended with no commits that a hand-off or an integration head does not already hold. The changes are read from its work tree; any hand-off of them is on its task, under Tasks.` — and shows its diff as any other session's, which is its work when a hand-off holds it and no changes when it made none ("Sessions"; ADR 0050). A `git` event refreshes that listing as well as the diff. The patch is drawn under a render budget, because a 1 MiB patch is tens of thousands of rows and nothing here is virtualised: a file of more than 500 changed lines opens collapsed, and past 2,000 changed lines in the whole patch every file opens collapsed whatever its own size, with a line above the blocks saying how many lines across how many files that was. Nothing is hidden by either bound — a collapsed file is one click from its hunks — and the file list, its counts and the truncation notice are unaffected. A diff row names what it is to a screen reader: the `+`/`-` marker is decorative, so an added or removed row carries the word instead, in both the unified and the side-by-side form, where there is no marker at all. Side by side is two scrolling panes rather than a scrolling row each, so a long line moves its whole side and the two versions stay level. After a successful push to a `github.com` remote the UI shows a link to `https://github.com/<owner>/<repo>/compare/<target>...<remote_branch>?expand=1`, built client-side from `remote_url`, next to the push result and on the session-branch list, with each `/`-separated segment of the two ref names percent-encoded so a branch carrying a `#`, `?` or `%` still compares. A push refused as non-fast-forward (409) is an answer and not a failure: it is shown once, as the advice to fetch and merge `origin/<the branch that was rejected>` — the name that was sent, not the one now in the field — and the server's own sentence is not repeated beside it. The session header shows `cost_usd` and the token counters, refreshed by the `session` frame that follows every `result`. A transcript `result` row shows the event's `cost_usd` as `total`, because it is the backend's running total and not the turn's own cost.

**Task board.** `useTaskStream(projectId)` installs SSE handlers, opens the stream with `?after=store.lastSeq` — `?after=latest` while that cursor is still 0 ("SSE: task stream") — and waits for `open` before loading the project's states and tasks through REST. On error it closes the stream and reconnects with the last received sequence, then refreshes again; the token is rotated on the first error of a run of failures only, and the attempts are bounded exactly as the session socket's are ("Authentication"). `stream` is therefore `reconnecting` only while an attempt is pending and `offline` once the stream has given up, with `streamError` saying why and a `Reconnect` action above the board; the snapshot underneath stays on screen, being the last thing the board really knew. Each new `TaskEvent` updates the receive cursor and invalidates the board snapshot; its payload is not applied directly to cards or columns. Columns are the project's states in `position` order. State renames, deletions and ordinary mutations all use the same refresh path. The board's header links the `task-flow` help topic, as the states editor's does. Cards show priority, labels, the holding session (with a link), attempts when above one, the round when above one (`round 2/5`, against the project's `max_rounds`), assignee, blocked and dependency indicators, and a parent badge. A task the dispatcher holds back for its author's work says so: when an open (`closed_at` null), unheld task's `created_by_session_id` names a session whose row in `GET /projects/{pid}/git/session-branches` has `ahead > 0`, its card and its drawer show a quiet line in the parked colour, `Waiting for session <title>'s branch to reach <default branch> (N commits)`, linking to the project's Branches tab, where the branch is merged. The rule is the dispatcher's (`ARCHITECTURE.md`, "Dispatcher" → "A task waits for its author's work"; ADR 0052): `ahead > 0` against the default branch is the author's tip not being contained in it. The session is named by its title from the project's cached session list, or by the first eight characters of its id. The line reads the session-branch list through the cache the Branches tab uses, and only for a task it could apply to; the board adds no git polling of its own, so the line goes away on that list's own refresh — a view mounting it stale, window focus, or a merge from the Branches tab invalidating it. Nor does a merge launch the task at once: a plain branch merge wakes no dispatcher run, so the task is launched by the next timer run, within `DISPATCHER_INTERVAL_SECS`. One gap is known: a live author session that has never synced has no ref, so the list has no row for it and the board shows no line while the dispatcher, which syncs the author silently before judging, already holds the task back; the ref that check creates puts the line on the board after one dispatcher run. A detail drawer shows description, comments (system comments styled apart), dependencies by kind, children, the sessions that touched the task with links into their transcripts, and actions: move to a state, release, "open in session", which picks a conversational profile (default: the first that serves the task's state) and launches it with `task_id`, and "run once", which does the same with an ephemeral profile. Both launch controls are disabled, carrying the reason, for a task that is held, blocked or in a terminal state and for a project that is not `ready` — the four refusals `POST /projects/{pid}/sessions` answers 409 for — so the user reads the reason before the request rather than after it. The project page's form and the drawer's are one launch: create, the two invalidations it settles — the project's session list and the task the launch claimed — and the navigation to the new session are shared, and neither form sends `base_ref` unless the user chose one. While a launch is in flight the two kind toggles and the open form's `Cancel` are disabled, so the request cannot have its form taken away mid-flight; a launch whose form is gone anyway, because the drawer closed on Escape or the user moved on, still creates the session and still settles both caches, and does not navigate away from wherever the user went. The drawer shows a task's attempts, once above one, against the project's `max_attempts` (`2/3`), the count at which an agent's or the reaper's release escalates it, and its rounds, once above one, against the project's `max_rounds` (`2/5`), the count at which a send-back by a session or a conflicting automatic merge escalates it. The session view shows the task the session was launched for and the tasks it touched in a side panel. `TaskStatesEditor` on the project page lists, adds, renames, reorders and removes states, with the deletion rules from the API surfaced as disabled actions — a state that is another's conflict state names that state as the reason. A `queue` state's row also carries an `Auto-merge` toggle and, while it is on, a `Conflict state` select over the project's other `queue` states, saved together in one `PUT`; turning the toggle on pre-selects `ready` when the project has such a queue state, otherwise the first other queue state, and the column header of an auto-merge state carries an `auto-merge` chip so the board says which column empties by itself. The project settings form edits `max_rounds` beside `max_attempts`.

Everything the drawer holds that is not the task itself — edit mode and its draft, the comment being written, an open confirmation or review — belongs to the task on display and is discarded when the drawer shows another one, including when that task is already cached and so appears without a loading state in between. A refresh of the *same* task, which every task event causes, keeps it: a draft is never lost to a refetch. The project page follows the same rule at the project's id, so a confirmation or a settings field opened on one project cannot be submitted against another. What such a control holds is the user's own choice and never a copy of the task: the move-to-state control stores the state the user picked, or nothing, so a task moved by an agent while the drawer is open carries the select with it and leaves Move disabled until somebody picks a state; a successful move puts it back to nothing.

The drawer is a modal: while it is open, nothing behind it can be reached with a pointer or a keyboard. Opening it moves focus to the task's heading, Tab and Shift+Tab stay inside it, and a link to another task moves focus to the heading again, because the body under it is replaced. Closing it gives focus back to the control that opened it; when there is none — a pasted link — or it is gone, focus goes to that task's card on the board, and failing that to the page's main region. Escape closes the drawer, except that it is ignored when another handler has already taken the key or it is ending an IME composition, it closes the innermost open sub-form — the edit form, a hand-off, review or merge form, the launch panel, a confirmation — before it closes the drawer, and over unsaved text it asks: the first press says so and the second one discards. Typing withdraws the question. A sub-form whose submission is in flight does not take the key, for the reason its own `Cancel` is disabled then: the request owns the form it was made from, and no one press may take its fields away.

**Task editing.** The drawer's edit form sends only the fields the user changed: a `PUT` leaves omitted fields alone ("Tasks"), so an untouched field is never written back and two people editing different fields of the same task do not overwrite each other. The baseline it compares against is the reading of the task the form opened on, captured with the draft fields and kept for as long as the form is open, so a board refresh or a task event arriving mid-edit ("Board refresh ordering") cannot widen a save to fields the user did not touch. Clearing the assignee or the parent is an explicit `null`; a save that changed nothing makes no request and just closes the form. When an editable field of the server's copy moves away from that baseline while the form is open, the form says so, and saving still carries only the fields edited there. Whether the task may be given a parent at all comes from the task's own `children`, not from the board snapshot.

**Task-board search.** Provide a labelled search field above the board with placeholder `Search title or #number` and a clear action. Trim surrounding whitespace: an empty query shows all tasks; a query consisting only of digits, optionally prefixed with `#`, matches the exact per-project task number; any other query matches a case-insensitive substring of the title. For example, `#42` and `42` match task 42, not 142; `login` matches `Fix Login Redirect`. Search spans all project state columns, including terminal states, and does not search descriptions or comments.

Apply search locally to the complete project task snapshot already loaded by the board. Keep the original snapshot intact; derive the visible cards while retaining column order and normal task ordering. Do not issue REST requests or reconnect SSE when the query changes. Keep the query through snapshot refreshes and reapply it to updated titles, new tasks and deletions. Reset it when changing projects. Preserve columns when there are no matches and show `No matching tasks` with the clear action; distinguish this from initial loading, a failed load or an empty project. Search does not close an already-open task drawer or prevent opening a task through its direct URL. No new API parameter, database index or search service is required (ADR 0031).

**Board refresh ordering.** For each mounted project view, allow at most one refresh at a time. Each refresh makes fresh REST reads of both task states and tasks through the services layer; replace both in the Zustand store together, together with the by-id and by-number indexes any lookup uses, so a lookup never describes the previous snapshot. A read cancels an outstanding request for the same key before making its own, so a refresh can never install a response that began before it did, and it takes the installed copy back out of the query cache, so a task that did not change is the same object it was in the previous snapshot.

At the start, capture the connection/view generation and the event generation. Every non-duplicate event increments the event generation. A response belonging to a view that has moved on — a reconnect, a project change or an unmount — is discarded. A response dirtied by an event that arrived while it was in flight is *installed* and followed by exactly one coalesced refresh: it is older than the event but, by the cancel-before-read rule above, strictly newer than what is on screen, and discarding it was what made a board under events arriving faster than a round trip install nothing at all for as long as the agents worked. A successful local mutation also invalidates the view, even if its SSE event has not arrived yet; both the mutation's refresh and the event's are whole snapshots and both are shown.

Read failures retain the previous snapshot and the dirty flag, show the ordinary error/retry state and retry through the query layer; they never install an empty board. Keep a loading state before the first successful load. Afterwards, say `Reconnecting` for as long as the stream is not live, but say `Refreshing` only for a refresh that has run past a short delay: the marker is one `role="status"`, and a refresh that is over before it can be read is a screen reader talking over the work it is reporting.

Delayed events cause another authoritative refresh rather than applying obsolete payloads. Open task details and related queries are invalidated on task events as well — on every kind, including the `states_changed` that carries no `task_id`, because a renamed state is exactly what an open drawer is showing the old name of. Those invalidations are coalesced into one flush per tick, however many events fall in it. The board's stream invalidates the task keys of its own project and nothing else; a query belonging to another view is refreshed where that view can observe it. This is eventual consistency through REST refreshes, with no new snapshot-cursor protocol or event buffer in v1.

**Hand-off controls.** Task details show the current source session/branch, pinned commit, comment and review status, plus hand-off history, under one line saying what a hand-off is that links `task-flow`. A code hand-off form selects a source session and exact commit, requires a comment, and submits it with the target state; its source field says that publishing syncs that session's branch and includes only committed work. Review actions forward the current hand-off id with `approved` or `changes_requested` and a comment. Neither action silently selects the reviewer's own branch. A review or merge form is about the hand-off it opened on and keeps naming that one for as long as it is open — the commit on its cover line, the source branch and the submitted `handoff_id` all come from that reading — so a revision published mid-form never retargets a decision the user has already made; the request carries the superseded id and the 409 above refuses it. A form whose hand-off is no longer the task's current one says so while it is still a choice, rather than swapping the commit underneath the comment. "Open in session" and "run once" default to the hand-off commit and visibly disclose any base override. Both launch forms say the base the same way — the hand-off's commit, branch and review status, or the project's default branch — and choose one with the same control, the grouped list of the mirror's refs plus a custom ref for a tag or commit id; in the drawer that control sits behind the `Override base ref` disclosure, and the empty entry of either is what the server would pick rather than a name copied into the form. The task's merge action sends `task_id` and `handoff_id` and is enabled only for an approved current hand-off, and its button's title says it merges that hand-off's commit, not the latest tip of its branch. Its form offers only integration heads the mirror really has: with none, the target is empty and Merge is disabled rather than sending the project's `default_branch` into a 400. A merge has one outcome — merged, conflicted or refused — and one that merged disables its own submit, so the commit cannot be merged twice from the same form. Approval is labelled with the commit it covers; new revisions appear unreviewed. The diff endpoint accepts `handoff_id` instead of `head` to view the retained commit without syncing a live branch. While the task has a current hand-off the section offers `Drop hand-off`, which opens an inline caution confirmation saying that the next launch for this task starts from the project's default branch and that the hand-off stays in the task's history; it holds a required comment field, refused before the request when empty, and its button names the task, `Drop hand-off of #<number>`. Confirming sends `POST .../drop-handoff` with that comment, and the drawer then shows `No code hand-off` with the dropped record still in the history.

**Composer.** A text area with submit on Enter (Shift+Enter for newline), disabled when the session is `done`/`failed` and absent for ephemeral sessions. An Enter that ends an input-method composition never submits: it is skipped both where the browser says the composition is still running and where it says nothing but the legacy key code 229, which is what Safari reports for the Enter that accepts a candidate. A message the transcript offers to resend — one refused, or lost with the connection — puts its text in the box and focuses it, replacing what is there. While a turn is in progress the button reads "Interject". Sending optimistically starts a turn, so a send the orchestrator refuses puts `turnActive` back as it was, unless another send is still in flight or an event has arrived since — the button goes back to reading "Send" on an idle session instead of waiting for a `result` that is not coming. A stop button sends `stop`. It is the same button the session header offers, with one behaviour between them (`session/useStopSession.ts`): a stop is a request, not a transaction (`ARCHITECTURE.md`, "Stop semantics"), so pressing either reads `Stopping…` and refuses a second press until the session leaves `running` or 30 seconds pass without an answer, after which it may be asked again. There is no answer mode: the agent never asks the host a question (ADR 0033), so the composer only ever sends a `message`, and one sent during a turn is queued by the CLI as the next turn rather than interrupting the current one (`ARCHITECTURE.md`, "Input encoding").

## Non-goals for v1

- GitHub App credentials, GitHub login, webhooks — and so the agent that would turn GitHub issues into backlog tasks, which needs them and nothing else: the two halves of automatic launching are both built and described under "Automatic dispatch" and "Scheduled agents".
- Egress restriction for session containers and sandboxed runtimes as defaults. `runtime` is configurable per profile; installing and choosing one is the operator's job.
- Isolation of orchestrator git operations on agent-controlled checkouts. v1 explicitly accepts the known vulnerability that repository-controlled git configuration can execute commands with orchestrator privileges; remediation is deferred (ADR 0019; `ARCHITECTURE.md`, "Known v1 vulnerability: git execution outside the session container").
- Durable input queues, delivery-status UI and restart-safe input deduplication. Input loss and uncertain or repeated processing around orchestrator restarts are accepted v1 limitations; normal output persistence and replay remain required (ADR 0020).
- Per-project authorisation. Every user sees every project.
- Multi-node orchestration or more than one orchestrator instance.
- A second agent backend. The `AgentBackend` trait exists so one can be added; GitHub Copilot CLI is the candidate and lives on the roadmap in `README.md`.
- Self-registration. Users exist only through invites.
- Secret injection through files instead of environment variables (documented hardening step).
- Automatic secret detection or redaction in transcripts and agent-produced event content. Such content may retain plaintext credentials; the secret-handling rules govern orchestrator diagnostics and credential storage, not a guarantee about arbitrary agent output (ADR 0027).
- Transcript export, search across sessions, cost reporting beyond the per-session counters.
- Per-profile CPU and memory limits.
- An MCP tool for the agent to set its own session title.
- Pagination of task and session lists.
- Mobile layouts beyond "does not break".
